The big picture

🌱 In plain words

Think of a website as a restaurant. Each web address is a table. Each table has a recipe card that says what to cook, how to take orders and what to do if something burns. React Router Framework Mode is the restaurant with the kitchen, waiters and front door already built.

Words to know

Framework
A ready-made toolkit that decides how the parts of an app fit together.
Route
One web address and the file that handles it.
Route module
That file: it holds the screen, the data fetching, the saving and the error handling.
Loader
Code that fetches a page's data before the page shows.
Action
Code that handles a form when someone submits it.

1.1 The restaurant

🏠The restaurant= the website
🔢A table number= a web address (URL)
📇The recipe card= the route module file
🍳The kitchen preparing the plate= the loader
🧾The order slip= the action
🧑The diner= the browser

1.2 The one big idea

🗄️ Server = the truth

The real data lives on the server.

📋 Browser = a copy

The browser only keeps a copy (a cache).

🔄 Auto refresh

After every successful save, React Router reloads the page's data for you.

Why it mattersYou rarely write extra "state management" code. The docs say most apps skip libraries like Redux or TanStack Query.

1.3 Three modes, like nesting dolls

React Router comes in three modes. Each one adds to the one inside it. Framework is the biggest doll.

🥕 Declarative

Buying the ingredients. You do the rest.

📦 Data

A meal kit: data loading, saving and loading states.

🍽️ Framework

The full restaurant: kitchen, waiters and front door included.

Which one?The docs frame it as "how much you want to do yourself". They recommend Framework mode if you are new or "just want to build something with React".

Framework-only parts are all about owning the whole HTML page:

<Links><Meta><Scripts>ServerRouterlink prefetching

Q Flashcards

What is Framework Mode, in one line?

Data Mode "wrapped with a Vite plugin" that adds type safety, automatic code splitting and a choice of SSR, SPA or static pre-rendering.

Server and browser: which holds the truth?

The server. The browser is a cache, and React Router refreshes it after saves.

Words to know

Terminal
The text window where you type commands.
Template
A ready-made starter project with the main files in place.
Dev server

3

The recipe card (route module)

🌱 In plain words

Each table has one recipe card. It says what the plate looks like, how to cook it, how to take orders and what to do if something goes wrong. In React Router that card is one file, the route module.

Words to know

Export
A named part a file offers to the outside, like one slot on the card.
Component
The screen itself: what the visitor sees.
Bundle
The code package sent to the browser.
Typegen
Auto-made type files so the editor catches wrong data shapes.

Every route has two required parts: a URL pattern and a file path to the route module. The file can have up to fifteen slots in three groups.

3.1 Three groups of slots

🔒 Server parts

loader fetches data · action saves forms · middleware wraps requests (for example a login check) · headers sets HTTP headers such as caching.

🌐 Browser mirrors

clientLoader, clientAction, clientMiddleware do the same jobs in the browser. HydrateFallback is a placeholder while browser data loads on the first visit.

📄 Page parts

ErrorBoundary is the safety net. meta, links, handle. shouldRevalidate lets the route skip automatic refreshes.

3.2 What the screen receives

loaderDataactionDataparamsmatches
Typegen: free type checksReact Router reads routes.ts and writes a +types/<route>.d.ts file for every route. react-router dev keeps them up to date, so your editor knows the shape of the page's data and URL parameters.
For developers
import type { Route } from "./+types/product";
// Route gives checked types for this page's
// loaderData, actionData and params
4

Routes and the picture frame

🌱 In plain words

Pages sit inside pages, like picture frames inside picture frames. The outer page leaves an empty frame, and the inner page fills it. When you move, only the frame that changed is redrawn.

Words to know

Nested route
A page inside a page.
<Outlet/>
The empty frame a parent leaves for its child.
Index route
The default child shown at the parent's own address.
Layout route
A shared frame (like a sidebar) that adds no words to the address.
Params
The variable part of an address, like the 1 in /products/1.

4.1 Frames inside frames

  1. 1Root draws the page shell. root.tsx is the only required route. It renders the real HTML page and leaves an empty frame, <Outlet/>.
  2. 2Dashboard fills that frame with its sidebar, and leaves a smaller frame.
  3. 3Settings fills the smallest frame. The address /dashboard/settings is now on screen.
  4. 4The address changes to /dashboard. Only the inner frame changes, now showing the index page. The header and sidebar stay where they are.

4.2 The address list: four helpers

Addresses live in app/routes.ts, the floor plan.

📍 route()

Maps one address to one file.

🏠 index()

The default screen at the parent's address.

🖼️ layout()

Adds a shared frame, but no words to the address.

🏷️ prefix()

Adds a word to the address, but no frame.

Spot the difference

4.3 Addresses with blanks

Variable

:teamId becomes params.teamId.

Optional

A trailing ? makes a part optional.

The rest

files/* captures the rest of the address.

Not found

route("*", ...) catches every unknown address for a 404 page.

Prefer folders?@react-router/fs-routes builds the same tree from file names such as _index.tsx, concerts.$city.tsx and _auth.login.tsx. Both styles can be mixed.

4.4 When something breaks: the safety net

Any route can export an ErrorBoundary. An error shows the nearest net at or above that route. Everything outside stays on screen, like a circuit breaker for each room.

Use error boundaries for

  • Unexpected failures (bugs)
  • Deliberate "not found" responses, like a 404

Don't use them for

  • Form validation: return those messages from the action as normal data
Safe by defaultIn production, real bug details are hidden from the browser. Messages you throw on purpose with data() are shown.
For developers
// app/routes.ts helpers
route("about", "./about.tsx")
index("./home.tsx")
layout("./auth/layout.tsx", [ /* children */ ])
...prefix("concerts", [ /* children */ ])
route("*", ...)            // every unknown address

// a deliberate "not found"
throw data("Record Not Found", { status: 404 });
// in the root ErrorBoundary: isRouteErrorResponse(error)

Q Flashcards

layout() vs prefix()?

layout adds a frame but no address word. prefix adds an address word but no frame.

An error in payments.tsx: which boundary shows?

The nearest one at or above it: invoice-page.tsx in the docs' example. Outer layouts stay on screen.

5

Moving between pages

🌱 In plain words

There are six ways to move to another page. To pick one, ask who starts the move: the visitor clicks, the visitor submits, the server decides, or a timer decides.

Words to know

Navigation
Moving from one page to another.
Redirect
The server sends the visitor somewhere else.
Prefetch
Loading the next page's code and data before the click.

5.1 Who starts the move?

👆 The visitor clicks

<Link><NavLink>

Link for a plain link. NavLink for menu links that highlight when active or pending.

📝 The visitor submits

<Form> (GET)<Form method="post">useFetcher()

GET forms for search boxes that put the query in the address. Post forms or fetchers to send data.

🗄️ The server decides

redirect()

After a loader or action, the server says where to go next.

⏱️ A timer decides

useNavigate()

Only when code must move with no visitor action, like an inactivity logout or a quiz timer. The docs say "use sparingly".

5.2 Prefetch: cook before the order

"none" (default)"intent": hover or focus"render""viewport"
For developers
<Link to="/products/2" prefetch="intent">Product 2</Link>
// prefetch: "none" (default) | "intent" | "render" | "viewport"
6

Loading data

🌱 In plain words

Before a plate is served, the kitchen prepares it. A loader fetches a page's data before the page shows. All the kitchen stations cook at the same time, not one after another.

Words to know

Loader
Server code that fetches a page's data before it shows.
clientLoader
The same idea, run in the browser (for public APIs or browser storage).
Waterfall
A slow chain where each request waits for the one before.
Middleware
Code that wraps every request in layers, like a login check.
Streaming
Sending the page in parts, so slow data fills in later.

6.1 Server loader or browser loader

🍳 loader

Runs on the server. Used for the first page load and for later clicks: React Router calls it from the browser with an automatic fetch.

🌐 clientLoader

Runs only in the browser. If a route has both, the server loader handles the first load and the client loader the later clicks. It can still call serverLoader().

📦 What it can return

Plain objects, including promises, maps, sets and dates. Or data(value, { status, headers }) to set an HTTP status.

6.2 All loaders run at once

The catchBecause loaders run in parallel, a parent loader cannot protect its children with a login check. Each loader must check the login itself, or middleware on a shared parent must do it.

6.3 Middleware: layers of an onion

AnalogyDoormen at each nested door. The outer one checks the reservation once, and everyone inside trusts the note he passes along. That note is the context.

  1. 1Root starts. The outer doorman, for example checking the login.
  2. 2Parent starts.
  3. 3Child starts. Each one calls next() to pass the request inward.
  4. 4The loaders run (all in parallel), reading the note from context.
  5. 5Child ends.
  6. 6Parent ends.
  7. 7Root ends. The response goes out.

6.4 Streaming: main course now, dessert later

Await the critical dataAnything above the fold or needed for search engines.
Return slow data unawaitedIts promise goes back inside an object.
Show a placeholder<React.Suspense fallback> with <Await>.
Time limitPromises still waiting are rejected after 4950 ms by default. Change it with export const streamTimeout in entry.server.tsx. The old defer() helper is gone.
For developers
// loader: set a status without building a full response
return data(value, { status, headers });

// middleware: call next(), share a typed note
createContext()   context.set(...)   context.get(...)

// streaming in the component
<React.Suspense fallback={...}>
  <Await resolve={promise}>...</Await>
</React.Suspense>

Q Flashcards

Why can't a parent loader guard its children?

All matched loaders run in parallel, so the child does not wait for the parent. Use middleware, or check in each loader.

What should be streamed?

Slow, non-essential extras like reviews or recommendations. Await what is above the fold or needed for search engines.

7

Saving data

🌱 In plain words

The diner hands over an order slip. The kitchen cooks it. Then every dish on the table is refreshed, so nothing is stale. You don't write the refresh code.

Words to know

Action
Server code that handles a form submission (saving, deleting).
Revalidation
Re-running loaders after a save so the screen shows fresh data.
Fetcher
A way to load or save without changing the address.
Pending UI
Spinners or dimming while something loads or saves.
Optimistic UI
Showing the expected result before the server confirms.

7.1 Submit, save, refresh

✅ Success (2xx)

Every active loader re-runs.

⛔ Failure (4xx or 5xx)

Refresh is skipped by default.

🎚️ Opt out

shouldRevalidate skips one route, but "can leave the UI out of sync with the server".

Do

  • Save through <Form> or a fetcher, so the page refreshes itself
  • Return validation errors from the action as data
  • Keep useRevalidator() for refresh on window focus or polling

Don't

  • Call an API with a plain fetch(): it skips the router, so nothing refreshes
  • Use an error boundary for form validation

7.2 Form goes somewhere, fetcher does something here

One test: should the address change?

🚪 Use <Form>

When the address should change, like creating a project and then going to its page. It adds a history entry and drives the global loading state.

💬 Use useFetcher

When it should not: marking a message read, deleting one row, loading a pop-up's data. Each fetcher has its own state, and many can run at once.

7.3 While you wait

Pending state

useNavigation, NavLink's isPending, and fetcher.state: idle, loading or submitting.

Optimistic UI

Read fetcher.formData to show the result straight away (tick the task), then let the server's fresh data take over.

Races handled

An interrupted move cancels data requests in flight, and an old answer never overwrites a newer one.

Your jobThe framework gives you the pending state, but "apps must implement pending and optimistic UI themselves".
For developers
<Form method="post">...</Form>     // address changes
const fetcher = useFetcher();     // address stays
<fetcher.Form method="post">...</fetcher.Form>
fetcher.state      // "idle" | "loading" | "submitting"
fetcher.formData   // for optimistic UI
fetcher.data       // what the action returned
// also: useSubmit, fetcher.submit, useRevalidator()

Q Flashcards

What happens after a successful action?

All loader data on the page is revalidated automatically, so the screen matches the server.

Form or fetcher: delete one row from a list?

A fetcher. The address should not change.

Three journeys

🌱 In plain words

Three trips show the whole machine at work: the first visit, a click to another page, and a form submit. Press Play, or tap a step card.

Words to know

Document request
The browser asking the server for a whole page.
Hydration
The browser "waking up" ready-made HTML by attaching JavaScript to it.
Progressive enhancement
Pages and forms work as plain HTML first, then get better with JavaScript.
NoteThe docs give no single official lifecycle diagram. This order is put together from the Data Loading, Middleware, Progressive Enhancement, Lazy Route Discovery and Actions pages.

8.1 Journey one: the first visit

  1. 1The browser asks the server for /products/1 (a document request).A diner walks in and gives a table number.
  2. 2Server middleware runs root to leaf, like an onion, for example checking the login.Doormen check the reservation at each door.
  3. 3React Router matches root → products → product and runs all matched loaders in parallel.Every kitchen station cooks at once.
  4. 4entry.server.tsx renders the pages into HTML with the data baked in, and starts streaming it.The meal goes out course by course.
  5. 5The browser paints the HTML straight away. Links and forms work even before JavaScript loads.The diner can eat before the waiter arrives.
  6. 6Only the code for this page's routes downloads (code splitting, lazy route discovery).Only this table's menu is printed.
  7. 7React hydrates: it attaches click handlers to the existing HTML. A clientLoader runs now only if clientLoader.hydrate = true, with HydrateFallback shown meanwhile.A painted stage set gets its lights switched on.
  8. 8Links on the page are discovered in one batched /__manifest request, and prefetched if prefetch is set.The waiter quietly learns the nearby tables' orders.

8.2 Journey two: a click to another page

  1. 1The visitor clicks <Link to="/products/2">. React Router catches it, so there is no full page reload.The diner moves tables without leaving the building.
  2. 2useNavigation() switches to loading, which the app can show as a spinner or progress bar.A "your food is coming" light turns on.
  3. 3If the route is unknown, its manifest and code are fetched first.The waiter fetches that table's recipe card.
  4. 4Matched loaders run in parallel. Server loaders are called through an automatic fetch (a .data request, which also runs server middleware).Only the changed dishes are cooked.
  5. 5Critical data is awaited; streamed parts fill in later under Suspense.Main course now, dessert when ready.
  6. 6Only the changed frames re-render, the address updates, and navigation returns to idle.The tablecloth stays and only the plates change.

8.3 Journey three: a form submit

  1. 1The visitor submits <Form method="post"> (or a fetcher form).The diner hands over an order slip.
  2. 2State becomes submitting. formData is available for an optimistic preview.The waiter says "coming right up".
  3. 3The route's action runs on the server (or clientAction in the browser).The kitchen cooks the order.
  4. 4aIf the action returns redirect("/projects/9"), the router goes there and runs that page's loaders.The diner is shown to a new table.
  5. 4bOtherwise its result arrives as actionData or fetcher.data, for example validation errors.The waiter reports back: "we're out of that".
  6. 5If successful (2xx), every active loader re-runs automatically. A 4xx or 5xx result skips this by default.Every dish on the table is refreshed.
  7. 6The screen re-renders with fresh data and the state returns to idle. Without JavaScript, the same form still posts as plain HTML.The bill updates itself.

Remember

  • First visit: HTML first, JavaScript later
  • Clicks: no full reload, only changed frames redraw
  • Submits: save, then everything refreshes
  • Forms work even without JavaScript
9

Rendering choices

🌱 In plain words

Where and when is the HTML page made? Cooked fresh for each visit, prepared ahead, or finished by the diner at home? One setting in react-router.config.ts picks it.

Words to know

SSR (server-side rendering)
The server builds finished HTML for each visit.
Pre-rendering
HTML built once, at build time, and served as files.
SPA mode
The browser builds the page from a nearly empty shell.
Build time
When you package the app, before anyone visits.

9.1 Three kitchens

🍳 Cook to order (SSR)

ssr: true (the default)

Builds HTML on every request. Needs hosting that can run a server.

🥡 Meal prep (pre-render)

prerender: ["/", "/about"]

Runs loaders at build time and writes an .html file for first visits plus a .data file for later clicks, for each address. Can also be true or a function that lists pages such as blog posts.

📦 Meal kit (SPA mode)

ssr: false

Builds only the root shell into index.html. All data work happens in the browser with clientLoader and clientAction. Cheap to deliver, but the diner does the cooking.

9.2 Pick one

What are you building?

Tap a choice to see the match.

The docs give no official decision chart. This guide is drawn from the trade-offs they state.

They combinessr: true plus a prerender list: listed pages are static, other pages are server-rendered as usual. ssr: false plus prerender: a static site with a single-page fallback.
SPA mode rulesNo headers or action exports. Server loaders only on the root (or on pre-rendered routes). The root still renders once at build time, so code must not touch window during the first render.
New and unstablev8.5.0 added a fourth option, ssr: "unstable_api-only": a server for loaders and actions, but only a root HTML shell is served.
For developers
// react-router.config.ts
ssr: true                       // default: cook to order
prerender: ["/", "/about"]      // or: prerender: true
ssr: false                      // SPA mode
ssr: "unstable_api-only"        // v8.5.0, unstable
10

Speed and going live

🌱 In plain words

Speed tricks come built in: each page ships only its own code. To go live you take one of two roads: a full server, or a plain file host.

Words to know

Code splitting
Downloading only the code the current page needs.
Lazy route discovery
Telling the browser about other routes only when links to them appear.
Adapter
Glue that runs the app on a given server platform.
Rewrite rule
A host setting that sends every address to one file.

10.1 Built-in speed

✂️ Per-route code

Each route is its own code bundle. Since v8, browser-only parts like clientLoader get their own chunks too (splitRouteModules, on by default).

🔭 Lazy route discovery

Sends only the routes needed for the first page. Helps most in apps with hundreds of routes.

🏷️ Cache headers

A route's headers export sets caching, like Cache-Control: max-age=3600, s-maxage=86400. The deepest route's headers win.

♨️ Hot reload

Vite keeps form inputs and other state while you edit code.

Why plain HTML firstThe docs put it in one line: "100% of your users have slow connections 5% of the time".

10.2 Two roads to go live

🖥️ Fullstack hosting

  • Official Docker templates: default, node-custom-server (Express), node-postgres (Postgres and Drizzle)
  • They run on AWS ECS, Google Cloud Run, Azure Container Apps, DigitalOcean, Fly.io or Railway
  • Vercel, Cloudflare Workers, Netlify and EdgeOne Pages keep their own templates
  • Adapters: @react-router/express, @react-router/architect (AWS), @react-router/cloudflare, and the built-in @react-router/serve used by npm start

🗂️ Static hosting

  1. Run react-router build
  2. Upload build/client to any file host
  3. Add a rule that sends every address to index.html
Pages give 404?If valid pages return 404 on a static host, the rewrite rule is missing.
Leave for laterReact Server Components are available but "experimental and subject to breaking changes in minor/patch releases".

What changed in v8

🌱 In plain words

v8 changes the floor, not the house. Routes, recipe cards, loaders, actions, fetchers, refresh, safety nets and the three kitchens all work the same. v8 raised the minimum versions, removed old names and made former options the default.

Words to know

Future flag
A switch to try next-version behaviour early. It becomes the default later.
Deprecated
Still works for now, but on its way out.
Unstable
An experiment that may change in any release.

  4. Only when prefetch is on
