M1

Introduction to Frontend System Design

🌱 In plain words

Think of building a house. You don't start by laying bricks: you ask the family what they need, draw a plan, decide where the pipes and wires go, then build. System design is the plan for an app. A junior engineer builds what they're told; a senior engineer makes the plan and explains why.

Words to know

Frontend
Everything that runs in the user's browser or app: what they see and touch.
Backend
The servers and databases the frontend talks to over the internet.
Requirement
Something the app must do (functional) or how well it must do it (non-functional).
Trade-off
Choosing one benefit means giving up another, like speed vs freshness.
Scale
How big it gets: users, data, features, teams.

Frontend system design is planning a web app before building it: which parts it has, how data moves, and how it stays fast, secure and usable as users, features and teams grow. Interviews test it in two rounds: LLD (build one component well) and HLD (design a whole product).

1.1 What it covers

🌐 Networking

How data reaches the browser: HTTP, REST, GraphQL, gRPC.

📡 Communication

Polling, WebSockets, SSE and webhooks for live data.

🔒 Security

XSS, CSRF, CORS, CSP and safe storage.

🧪 Testing

Unit, integration and end-to-end tests that catch bugs early.

⚡ Performance

Core Web Vitals, smaller bundles, faster rendering.

🗄️ Data and caching

Where to keep data in the browser and how long to trust it.

📈 Monitoring

Logs, errors and real-user metrics after release.

♿ Accessibility

Usable by keyboard, screen reader and everyone.

📴 Offline

Service workers and PWAs that work without a network.

1.3 A framework for any design question

A common order for a 45–60 minute interview is RADIO: it keeps you from jumping into code before you know what to build.

RADIO
  • Requirements
  • Architecture
  • Data model
  • Interface (API)
  • Optimizations
RequirementsAsk questions. Functional (what it does) and non-functional (devices, scale, offline, accessibility). Agree on scope.
ArchitectureDraw the main parts: components, state store, API layer, server, CDN.
Data modelThe entities and their fields; what lives on the server and what is client state.
InterfaceThe APIs between client and server, and component props.
OptimizationsPerformance, caching, accessibility, security, offline, monitoring.

Do

  • Spend the first 5–10 minutes on requirements
  • Say your assumptions out loud
  • Name the trade-off behind each choice
  • Keep an eye on time and cover every step

Don't

  • Start coding before the scope is agreed
  • Name tools without saying why
  • Go deep on one part and run out of time
  • Forget accessibility, errors and loading states
TipEvery module in these notes maps to a part of RADIO: networking and communication feed the Interface, caching feeds the Data model, and performance, security, testing, monitoring, accessibility and offline are Optimizations.

Q Flashcards

LLD or HLD: "build an autocomplete search box"?

LLD: one component, with its props, state, debouncing, keyboard support and edge cases.

What does RADIO stand for?

Requirements, Architecture, Data model, Interface (API), Optimizations.

Functional vs non-functional requirement?

Functional: what the product does ("users can post a comment"). Non-functional: how well ("loads in under 2 s on 4G", "works offline", "screen-reader friendly").

Why ask questions before designing?

The same prompt can mean a weekend project or a product for millions. Scope decides the architecture.

? Practice questions

The interviewer says: "Design a news feed." What should you do first?
  1. Pick React and start writing the Feed component
  2. Draw the database schema
  3. Ask about scope: post types, devices, real-time updates, scale
  4. Explain how you'd add a CDN
C. Requirements come first. Without them you can't choose between, say, polling and WebSockets, or decide whether offline support matters.

S Senior engineer level

What interviewers expect from a senior engineer on this topic, beyond the basics above.

🧭 Drive the conversation

  • Lead with questions, then propose scope and confirm it
  • Write requirements on the board before any boxes
  • Keep a visible checklist so you cover every RADIO step

⚖️ Think in trade-offs

  • For every choice, name the option you rejected and why
  • Tie choices to the requirements: "because users are on 3G…"
  • Say what you'd measure to know it worked

📐 Beyond the code

  • Non-functional needs: performance budgets, accessibility, security, i18n
  • Team scale: design system, ownership, CI, code review
  • Rollout: feature flags, monitoring, rollback plan

Senior interview questions

What separates a senior answer from a mid-level one in a design round?

Seniors set the scope, make trade-offs explicit, cover non-functional needs (performance, accessibility, security, monitoring) without being asked, and connect decisions to users and the business, not just to code.

You have 45 minutes. How do you split the time?

Roughly: 5–10 min requirements, 10 min architecture, 5–10 min data model and APIs, 15 min deep dives and optimizations, a few minutes to summarise and mention what you'd do next.

The basics

Frontend system design interviews ask you to design frontend systems, not distributed backends. They focus on architecture, not coding (Front End Interview Handbook). You generally do not design database schemas, choose SQL vs NoSQL, or talk about sharding and fault tolerance (Front End Interview Handbook).

There are two kinds of questions (Front End Interview Handbook):

KindExamplesCovered in
UI component (LLD)Autocomplete, image carousel, dropdown, modal, rich text editor, data table, poll widgetModule 11
Application (HLD)News feed, e-commerce, chat, photo sharing, collaborative editor, video streaming, video conferencing, spreadsheetModule 12

Analogy. A backend architect designs the power station and the grid. A frontend architect designs the house: the rooms (components), the wiring inside the walls (state and data flow), the socket that connects to the grid (the API), and the safety rules (security, accessibility, performance).

Beyond interviews: the architect's job

The same RADIO steps map onto a design document: context and goals, architecture diagram, data and state model, API contract, then risks and optimizations BK. Architects also own cross-team concerns: the design system, micro-frontends, the build and deploy pipeline, and performance budgets BK. Decisions are recorded as Architecture Decision Records (ADRs): short numbered documents with Title, Context, Decision ("We will…"), Status and Consequences, stored in the repo and superseded rather than rewritten (Cognitect, Nygard 2011).

Checklist: first five minutes of any design question
  1. Restate the problem and announce the RADIO plan.
  2. Ask: who are the users, what devices, what network (mobile 3G? offline?).
  3. Ask: what scale (items per page, concurrent editors, messages per second)?
  4. Pick 3–4 core features. Say what is out of scope.
  5. Write non-functional targets as numbers (Web Vitals, WCAG 2.2 AA, offline time, supported browsers, RTL).
Key takeaways
  • Frontend system design = client architecture + client–server contract + quality attributes.
  • RADIO gives structure. The deep dive (Optimizations) is where seniors win.
  • Raise performance, accessibility, i18n and security before you are asked.
  • Every choice needs a trade-off and a trigger for changing it.

Interview questions with model answers

How is frontend system design different from backend system design?

The focus is the client, its components, state and data model, and the API between client and server. We usually skip DB schemas, sharding and server scaling. We go deep on rendering strategy, caching, real-time transport, performance, accessibility and security.

Walk me through how you approach a design question.

I use RADIO. I clarify requirements and write non-functional targets as numbers. I draw the architecture. I define the data model and who owns each piece of state. I define component and server APIs. Then I spend the most time on two or three deep dives, such as performance or offline, and I close with trade-offs and what I would add next.

What do you do when the interviewer gives a vague prompt like "design Instagram"?

I narrow it. I pick the feed, posting a photo and likes, and I say stories and DMs are out of scope. I ask about device mix and network, then confirm the scope with the interviewer before drawing anything.

Meta 2020

rebuilt facebook.com on one stack

Illustrates: The idea in one line, The basics

What Rebuilt facebook.com on React, GraphQL and Relay, with atomic CSS-in-JS (later called StyleX) and code split into loading tiers.

Why The old site was slow and had grown inconsistent. The goals were "as little as possible, as early as possible" (paraphrased) and a better developer experience. The old homepage loaded over 400 KB of compressed CSS, and only about 10% of it was used for the first render.

Networking

🌱 In plain words

Loading a web page is like ordering from a restaurant you've never visited. First you look up its address (DNS), walk there and say hello (TCP), agree on a secret language so nobody can listen in (TLS), then place your order (HTTP request) and get your food (response). REST, GraphQL and gRPC are three different menus: fixed dishes, build-your-own plate, or a fast kitchen-to-kitchen order system.

Words to know

IP address
The number that identifies a computer on the internet, like a street address.
DNS
The internet's phone book: turns example.com into an IP address.
Protocol
Agreed rules for how two computers talk.
HTTP
The protocol of the web: requests with a method and URL, responses with a status code and body.
API
The set of requests a server accepts and what it sends back.
JSON
A text format for data: {"name": "Asha"}.

Every screen waits on the network. First what happens between pressing Enter and seeing a page, then the three main ways a frontend talks to a backend: REST, GraphQL and gRPC.

2.1 How the web works

Typing https://example.com and pressing Enter starts a chain: find the server's address, open a connection, secure it, ask for the page, then turn the reply into pixels.

DNS: turning a name into an IP address

Browser and OS cachesLooked up recently? Use the cached IP until its TTL runs out.
Recursive resolverYour ISP's or a public one (1.1.1.1, 8.8.8.8) does the lookup for you.
Root serverDoesn't know the IP, but knows who runs .com.
TLD serverPoints to example.com's authoritative name server.
Authoritative serverReturns the record (A for IPv4, AAAA for IPv6). Every layer caches it.

The layers a request travels through

HTTP application: methods, headers, status codes, body
TLS security: encryption and the server's certificate (the S in HTTPS)
TCP or UDP transport: TCP gives reliable, ordered delivery; HTTP/3 uses QUIC over UDP
IP network: routes packets to the server's IP address

From HTML to pixels

CSS → CSSOMCSS blocks rendering until it has loaded.
Render treeDOM plus CSSOM: only the visible nodes.
LayoutThe size and position of every box.

2.2 REST

REST (Representational State Transfer, from Roy Fielding's 2000 dissertation) is an architectural style, not a protocol. Everything is a resource with its own URL, changed with standard HTTP methods. The server sends back a representation, usually JSON.

📐 Constraints that make it REST

  • Client–server: UI and storage evolve separately
  • Stateless: each request carries everything, such as the auth token; no session on the server
  • Cacheable: responses say if and how long they can be cached
  • Uniform interface: resources named by URLs
  • Layered: CDNs, proxies and load balancers can sit in between

🔗 Designing the URLs

  • Nouns, not verbs: GET /users/42, not /getUser?id=42
  • Plural, nested for ownership: /users/42/orders
  • Filter and page with the query: /orders?status=paid&page=2
  • Version it: /v1/orders or a header
  • The method says what happens; the URL says to what

Strengths

  • Simple; works everywhere HTTP does
  • HTTP caching for free: GET responses cache by URL in the browser and CDN (Cache-Control, ETag → 304)
  • Easy to debug in the Network tab

Weaknesses

  • Over-fetching: /users/42 returns 30 fields when the card shows 3
  • Under-fetching: one screen needs several calls (user, orders, items)
  • A new response shape needs a new version or endpoint

2.3 GraphQL

GraphQL is a query language for APIs, built at Facebook and open-sourced in 2015. The server publishes a typed schema; the client sends one query to a single endpoint (usually POST /graphql) naming exactly the fields it needs, nested as deep as the screen needs. The response has the same shape as the query.

# Schema (server)
type User  { id: ID!  name: String!  orders(last: Int): [Order!]! }
type Order { id: ID!  status: String!  total: Float! }
type Query { user(id: ID!): User }

# Query (client): one request for the whole widget
query {
  user(id: "42") {
    name
    orders(last: 3) { id status }
  }
}

# Response: same shape as the query
{ "data": { "user": { "name": "Asha",
    "orders": [{ "id": "7", "status": "SHIPPED" }, …] } } }

🔎 Query

Reads data. Like GET, but you choose the fields.

✏️ Mutation

Writes data, then returns the fields you ask for.

📡 Subscription

Real-time updates from the server, usually over WebSockets.

TermMeaning
Schema (SDL)The typed contract of every type and field. Clients can read it (introspection), which powers autocomplete and generated TypeScript types.
ResolverA server function that fetches the data for one field. Nested fields call nested resolvers.
FragmentA reusable set of fields. Each component declares what it needs; the page combines them into one query.
Normalized cacheApollo Client and Relay store objects by type and id, so updating one order updates every screen that shows it.
TrapGraphQL servers often answer HTTP 200 even when something failed: the problems are in an errors array, sometimes next to partial data. Checking res.ok alone misses them.

Strengths

  • No over- or under-fetching: one round trip shaped like the screen
  • Strong types end to end, with tooling and codegen
  • Add fields without versioning; mark old ones @deprecated
  • One API serves web, mobile and other clients

Costs

  • HTTP caching is harder: one POST URL, so CDNs can't cache by URL (persisted queries over GET help)
  • N+1 queries on the server: one database call per list item, fixed by batching with DataLoader
  • Clients can send very expensive queries, so servers need depth and complexity limits
  • More setup than plain REST for a small API

2.4 gRPC

gRPC is a remote procedure call framework, open-sourced by Google in 2015. Instead of resources, you call methods on a service as if they were local functions. The contract is a .proto file; data travels as compact binary Protocol Buffers over HTTP/2.

syntax = "proto3";

service UserService {
  rpc GetUser (GetUserRequest) returns (User);          // unary
  rpc WatchOrders (WatchRequest) returns (stream Order); // server streaming
}

message GetUserRequest { string id = 1; }
message User {
  string id   = 1;  // field numbers, not names, go over the wire:
  string name = 2;  // never reuse or renumber them
}
Call typeShapeExample
UnaryOne request, one responseGet a user
Server streamingOne request, a stream of responsesLive order status, a large export
Client streamingA stream of requests, one responseUploading sensor readings
BidirectionalBoth sides stream at onceChat, multiplayer state
🌐 BrowserCalls the backend with REST or GraphQL, as JSON.
🧩 BFF or API gatewayA backend-for-frontend shapes data for the UI.
⚙️ Internal servicesTalk to each other with gRPC: fast, typed, streaming.
KeyBrowsers can't call a gRPC service directly: JavaScript can't control the HTTP/2 frames and trailers gRPC relies on. The browser uses gRPC-Web through a proxy such as Envoy, which supports unary and server-streaming calls only. That's why gRPC lives mostly between backend services.

Strengths

  • Small and fast: binary payloads, multiplexed HTTP/2
  • Generated, typed clients in many languages from one .proto
  • Built-in streaming, deadlines and cancellation

Costs

  • Not human-readable: hard to inspect in the Network tab or with curl
  • Needs gRPC-Web and a proxy for browsers
  • No HTTP caching by URL

Q Flashcards

What happens, in order, before the first byte of HTML arrives from a new site?

DNS lookup, TCP handshake, TLS handshake, then the HTTP request. Repeat visits skip steps thanks to DNS caching and connection reuse.

Why is HTTP/2 faster than HTTP/1.1 for a page with 80 assets?

It multiplexes many requests over one connection, instead of about 6 connections each doing one request at a time, and compresses headers.

PUT or PATCH to change just a user's email?

PATCH: it changes some fields. PUT replaces the whole resource and is idempotent; PATCH isn't guaranteed to be.

401 or 403?

401: we don't know who you are (log in). 403: we know who you are, and you're not allowed.

What's the N+1 problem in GraphQL, and the usual fix?

Resolving a list of N items triggers one extra database call per item. Batch the calls with DataLoader.

Why don't browsers call gRPC services directly?

JavaScript can't control the HTTP/2 frames and trailers gRPC needs. Use gRPC-Web through a proxy such as Envoy (unary and server streaming only).

  4. Paginate the orders endpoint
B. The cost is the number of round trips (under-fetching) plus unused fields (over-fetching). One GraphQL query returns the nested data in a single trip, and each screen picks its own fields. gRPC needs a proxy from the browser and doesn't reduce the trips; caching only helps repeat visits; pagination doesn't remove the extra calls.
This code shows "Hello, undefined" when the user doesn't exist, and the catch block never runs. Why?
try { const u = await (await fetch("/api/users/999")).json(); show(u.name); } catch { showError(); }
  1. The browser cached an old response
  2. await is missing before fetch
  3. fetch resolves on a 404; the code never checks res.ok
  4. The server should return 200 with an error message instead
C. fetch only rejects when the request can't complete. A 404 resolves with res.ok === false, and its JSON body has no name. Check res.ok and throw. Returning 200 for errors would make it worse.
The network drops while a request is in flight, and the client retries it automatically. Which request is safe to retry without risking a duplicate change?
  1. POST /orders
  2. POST /payments
  3. PATCH /cart with { "addItem": 7 }
  4. DELETE /orders/7
D. DELETE is idempotent: deleting order 7 twice leaves the same state as once. POST creates something new each time, and a PATCH that adds an item adds it again. To retry a POST safely, send an idempotency key the server can deduplicate on.

The basics: what happens when you type a URL

The steps below are the standard explanation. The notes mark them as background knowledge because the Cloudflare TLS page could not be fetched BK:

  1. Parse the URL and check HSTS (force HTTPS).
  2. Check caches: service worker, then the HTTP cache.
  3. DNS lookup: browser, OS, resolver, then root → TLD → authoritative server.
  4. TCP three-way handshake (1 round trip), or QUIC for HTTP/3.
  5. TLS 1.3 handshake (1 round trip; TLS 1.2 needed 2). 0-RTT resumption exists but has a replay risk, so allow it only for idempotent GETs.
  6. Send the HTTP request and wait for the first byte (TTFB).
  7. Stream and parse HTML into the DOM. The preload scanner finds resources early. CSS builds the CSSOM. Then render tree → layout → paint → composite (Module 6).

On a cold HTTPS connection over TCP, about 3 round trips pass before the first response byte (DNS + TCP + TLS 1.3). HTTP/3 merges transport and crypto into about 1 round trip BK.

Analogy. Bandwidth is the width of a road. Latency is the distance. Widening the road does not help if every delivery needs three phone calls before the truck may leave. Interview questions with model answers

Why is HTTP/2 faster than HTTP/1.1, and why do we need HTTP/3?

HTTP/2 multiplexes many streams on one connection, so there is no six-connection queue and no HTTP-level head-of-line blocking. HPACK shrinks repeated headers. But it still runs on TCP, so one lost packet stalls every stream. HTTP/3 runs on QUIC, where loss stalls only one stream, the handshake is shorter, and the connection survives a network change. That helps most on lossy mobile networks.

Should we still bundle everything into one file or shard domains?

No. Those were HTTP/1 workarounds. On HTTP/2 and HTTP/3 we want one origin to reuse the connection, and smaller chunks so a change in one module does not invalidate the whole cache.

How would you make the LCP image load faster?

Put it in the HTML, not behind JavaScript. Add fetchpriority="high" and never lazy-load it. Preconnect to the image CDN. Use 103 Early Hints if the HTML is server-rendered. Serve responsive AVIF or WebP from a CDN. Google Flights went from 2.6 s to 1.9 s with fetchpriority alone.

REST or GraphQL for our app?

REST plus a BFF if there are few clients and CDN caching matters. GraphQL if many clients need different shapes of deeply nested data, and the team can run query cost limits and persisted queries. tRPC for a single TypeScript monorepo team. gRPC-Web only if the backend is already gRPC.

What is the difference between preload and prefetch?

Preload fetches something the current page needs now, at high priority. Prefetch fetches something the next page will probably need, at low priority. Using prefetch for the current page, or preload for the next page, wastes bandwidth or delays critical work.

Communication

🌱 In plain words

Imagine waiting for a parcel. Short polling is calling the shop every 5 minutes: "Is it here yet?" Long polling is calling once and the shop keeps you on hold until it arrives. SSE is subscribing to SMS updates: they text you whenever something changes. A WebSocket is an open phone line where both of you talk any time. A webhook is the courier calling the shop's office, not you.

Words to know

Real time
Updates arrive within moments, without the user refreshing.
Push vs pull
Pull: the client asks. Push: the server sends without being asked.
Connection
An open channel between browser and server; keeping many open costs server memory.
Latency
The delay between something happening and the user seeing it.
Backoff
Waiting longer between each retry so you don't hammer a struggling server.

Plain HTTP is request–response: the server can only answer when the client asks. Chat, notifications, live scores and stock prices need the server to push updates. There are four main ways to get them: short polling, long polling, WebSockets and Server-Sent Events. Webhooks do the same job between servers.

3.1 Short polling

The client asks again on a timer, for example every 5 seconds, whether or not anything changed.

setInterval(async () => {
  const res = await fetch("/api/notifications?since=" + lastId);
  render(await res.json());
}, 5000);

Good

  • Simplest; works with any server and CDN
  • Fine when updates are rare and a delay is OK

Costs

  • Most requests come back empty: wasted traffic and server load
  • Updates arrive up to one interval late
  • Battery drain on phones

3.2 Long polling

The client asks, and the server holds the request open until there is news (or a timeout, around 30 s). As soon as the answer comes back, the client asks again.

Client asksGET /updates
Server waitsKeeps the request open, no reply yet
Event happensServer replies with the data, or empty on timeout
Client asks againStraight away
KeyLong polling gives near-real-time updates over plain HTTP, so it works through proxies and firewalls. The cost is one open connection per waiting client on the server, and a new request after every message.

3.3 WebSockets

A WebSocket starts as an HTTP request with an Upgrade: websocket header. The server answers 101 Switching Protocols, and the same TCP connection then stays open for messages both ways, at any time, with tiny frame headers.

const ws = new WebSocket("wss://chat.example.com/room/42");
ws.onopen    = () => ws.send(JSON.stringify({ type: "join" }));
ws.onmessage = (e) => addMessage(JSON.parse(e.data));
ws.onclose   = () => reconnectWithBackoff();   // you write the reconnect logic

Good

  • Full duplex: client and server both send whenever they want
  • Low latency and little overhead per message
  • Text or binary data

Costs

  • Stateful connections are harder to load-balance and scale (sticky sessions, a pub/sub layer)
  • No automatic reconnect: you build it, with backoff
  • No HTTP caching; some corporate proxies block it

3.4 Server-Sent Events (SSE)

The server keeps one HTTP response open and streams events as text (Content-Type: text/event-stream). It is one-way: server to client. The browser's EventSource reconnects automatically and resends the last event id.

const es = new EventSource("/api/scores");
es.onmessage = (e) => updateScore(JSON.parse(e.data));

// what the server writes, one event per blank-line-separated block:
// id: 17
// data: {"home": 2, "away": 1}
TrapOver HTTP/1.1 a browser allows only about 6 connections per domain, and every open SSE stream uses one, so many tabs can block other requests. HTTP/2 multiplexes streams over one connection, which removes this limit in practice.

3.5 Webhooks

A webhook is a server-to-server callback: you give a service (Stripe, GitHub) a URL, and it sends an HTTP POST to it when something happens. The browser isn't involved; your backend then tells the browser using one of the methods above.

Payment servicePayment succeeds

TrapWebhooks can arrive twice, late or out of order. Verify the signature, answer quickly with 2xx, and make the handler idempotent (ignore an event id you've already processed).

The basics

"Communication" means how the client and server talk after the page loads, and how tabs and threads in the browser talk to each other.

Analogy. Short polling is a child asking "Are we there yet?" every five minutes. Long polling is asking once and waiting until the driver answers. SSE is the car radio: the station talks, you listen. WebSocket is a phone call: both sides talk any time. WebTransport is a call with several lines at once, where some lines may drop a word to stay fast. A webhook is the post office calling your office, not your phone.

The transports

Server-Sent Events (SSE). Plain HTTP with text/event-stream. Fields are data, event, id and retry; lines starting with : are comments you can use as heartbeats. The browser reconnects automatically, and close() stops it. Proxies need buffering turned off (for example X-Accel-Buffering: no) (MDN SSE). On HTTP/1.x there is a hard limit of 6 connections per browser per domain, shared across all tabs, which Chrome and Firefox marked "Won't fix". On HTTP/2 the limit is negotiated, default 100 streams (MDN SSE).

WebSocket. Two-way and Baseline since 2015 (MDN WebSockets). Two traps: the WebSocket interface has no backpressure, so fast incoming messages can fill memory or peg the CPU, and an open WebSocket may keep the page out of the back/forward cache, so close it when the user leaves (MDN WebSockets).

WebTransport. Runs over HTTP/3/QUIC. It offers several reliable streams plus unreliable datagrams ("latest value wins" data, like game state), stream priorities, backpressure, and survival across network changes. It needs an HTTP/3 server library. It became Baseline 2026 ("newly available") in March 2026, so older browsers may lack it (MDN WebTransport). Safari support was not confirmed in the research unverified. Keep a WebSocket fallback.

How real systems do it

Slack. Each client holds one WebSocket to the nearest edge region. Envoy forwards it to a stateful Gateway Server that holds the user's subscriptions. Channel Servers own channels by consistent hashing (about 16 million channels per host at peak) and are replaced in under 20 seconds on failure. Sending goes through the HTTP API; receiving is WebSocket fan-out. Typing events are not stored. Messages reach anyone worldwide in about 500 ms (Slack Engineering).

Figma. Clients talk to one server process per document over WebSockets. The server decides the order of events. Figma rejected Operational Transformation (OT) as overkill and uses a CRDT-inspired, last-writer-wins-per-property model. Local edits apply at once. Client-generated IDs allow offline creation. On reconnect, the client downloads a fresh document, reapplies its offline edits and opens a new socket (Figma, archived). Figma later rewrote the multiplayer server from TypeScript to Rust (Figma blog, via a search summary).

Reliability rules for persistent connections

These are standard practice, not verified figures BK:

  • Reconnect with exponential backoff and jitter (1 s, 2 s, 4 s… capped near 30 s). Resume from the last event ID or sequence number. After a long gap, refetch a snapshot (as Figma does). Pause when the tab is hidden; reconnect on online and visibilitychange.
  • Heartbeats every 15–30 s (ping/pong or an SSE comment) keep proxies with ~60 s idle timeouts from killing the connection, and detect half-open sockets.
  • Backpressure: check WebSocket.bufferedAmount before sending. Coalesce on the client: send only the latest cursor position, throttled to animation frames. Use WebTransport when you need real stream backpressure.
  • Scaling: sticky sessions or connection-aware load balancing; a pub/sub backplane (Redis, NATS, Kafka) to fan out across gateway nodes; a separate stateful gateway tier like Slack's. Measure capacity in open connections, not requests per second.
Inside the browser: tabs, frames and workers
  • BroadcastChannel: named pub/sub between same-origin tabs, iframes and workers. It is limited to the same storage partition, so a b.com iframe inside a.com cannot talk to a top-level b.com tab. Baseline since March 2022 (MDN).
  • One connection per user, not per tab BK: elect a leader tab with the Web Locks API or BroadcastChannel and share messages, or own the socket in a SharedWorker. This avoids the six-per-origin SSE limit and N times the server load.
  • window.postMessage BK: for a specific window or iframe across origins. Always set targetOrigin and check event.origin exactly (Module 4).
  • Web Workers BK: move CPU-heavy work (big JSON parsing, diffing, search indexing, image processing, CRDT merges) off the main thread to protect INP. Transferables avoid copies. Workers have no DOM.
Checklist: real-time feature review
  1. What direction and how often? Pick from the table.
  2. Reconnect with backoff + jitter, resume from last ID, snapshot after long gaps.
  3. Heartbeat interval below the proxy idle timeout.
  4. One connection per user, shared across tabs.
  5. Messages carry client IDs so retries are idempotent.
  6. Throttle or coalesce high-frequency events (cursors, typing).
  7. Close the connection on pagehide so bfcache works.
  8. Fallback transport for old browsers or strict networks.
Key takeaways
  • Choose by direction, frequency and latency. Start simple.
  • SSE is underrated: plain HTTP, auto-reconnect, ideal for feeds and LLM streaming.
  • WebSocket has no backpressure and breaks bfcache if left open.
  • Real systems split send (HTTP) and receive (WebSocket fan-out) and use a stateful gateway tier.

Interview questions with model answers

Design a chat app. Which transport?

WebSocket for receiving messages, typing and presence. Each message carries a client-generated ID so retries are idempotent and the UI can be optimistic. Reconnect with backoff, then resync from the last sequence number. Share one socket per user across tabs. Fall back to long polling. Like Slack, I can send through the HTTP API and use the socket for fan-out.

Live notifications or a stock ticker?

SSE. It is one-way, plain HTTP and reconnects by itself with Last-Event-ID. On HTTP/1.1, the six-connection limit is shared across tabs, so I would serve it over HTTP/2 or share one connection across tabs.

How do you stream an LLM response?

SSE, or fetch with a streaming body. Render tokens as they arrive, and let the user stop with AbortController.

Polling or WebSocket for order status?

Polling or SSE is enough if the status changes every few minutes. A socket is overkill. But I would show the cost: a million users polling every 10 seconds is 100k requests per second.

How do you sync logout across tabs?

Send a logout message on a BroadcastChannel, with the storage event as a legacy fallback. Also revoke the session on the server so other devices log out too.

Collaborative editor: OT or CRDT?

For rich text, OT (with a central server, like Google Docs) or a CRDT library such as Yjs or Automerge. For object and property editing, a server-authoritative last-writer-wins model, as Figma uses, is simpler. I would also cover offline edits, resync on reconnect, and presence on a separate lossy channel.

Security

🌱 In plain words

Your website is a shop. XSS is a thief hiding a note in the suggestion box that, when the shop reads it aloud, tells staff to hand over the till keys. CSRF is a stranger forging your signature on a form while you're still logged in at the bank. CORS is the bouncer's guest list that says which other sites may read your shop's replies. Security headers are the shop's locks and rules posted on the door.

Words to know

Origin
Scheme + host + port, like https://shop.com:443. Different origin = different site to the browser.
Script injection
Getting your own code to run inside someone else's page.
Cookie
A small piece of data the browser stores and sends back to the same site, often your login session.
Token
A string that proves who you are, sent with requests.
Header
Extra information on an HTTP request or response, like Content-Type.

The browser runs code and stores data on a device you don't control, so the frontend is a big part of an app's attack surface. The main threats: XSS (running someone else's script on your page), CSRF (making the user's browser send a request they didn't intend), clickjacking, leaked tokens and risky dependencies.

4.1 Cross-site scripting (XSS)

An attacker gets their JavaScript to run on your page, usually through user content that is inserted as HTML. Once it runs, it can read anything the page can: the DOM, localStorage, non-HttpOnly cookies, and make requests as the user.

💾 Stored

The script is saved on the server (a comment, a profile name) and runs for every visitor.

🔁 Reflected

The script is in a URL parameter that the server echoes back into the page.

🧩 DOM-based

Frontend code puts URL or user data into the DOM unsafely, for example with innerHTML.

// ❌ runs any <img src=x onerror=…> inside comment.text
el.innerHTML = comment.text;

// ✅ treated as plain text
el.textContent = comment.text;

// ✅ when you really need HTML: sanitize first
el.innerHTML = DOMPurify.sanitize(comment.html);
KeyReact escapes text in JSX by default. The holes are dangerouslySetInnerHTML, href values like javascript:… built from user input, and third-party scripts.

4.3 CSRF and cookies

Cross-site request forgery: while you're logged in to your bank, an evil page submits a hidden form to the bank. The browser attaches your bank cookie, so the request looks real.

4.4 CORS

The same-origin policy stops a page from reading responses from another origin (scheme + host + port). CORS lets a server relax that: it answers with Access-Control-Allow-Origin. For non-simple requests (JSON body, custom headers, PUT/DELETE) the browser first sends an OPTIONS preflight.

TrapCORS is not a server-side security control: it only tells browsers whether a page may read the response. curl or a server ignores it. And Access-Control-Allow-Origin: * can't be used with credentials (cookies).

4.5 Storage, iframes and dependencies

🔑 Tokens in the browser

  • localStorage is readable by any script on the page, so XSS can steal tokens there
  • An HttpOnly, Secure, SameSite cookie keeps the session out of JavaScript's reach
  • Never store secrets (API keys) in frontend code: anyone can read the bundle

🖼️ Iframes

  • Embedding others: use sandbox and only allow what's needed
  • Being embedded: block with frame-ancestors
  • postMessage: always check event.origin

📦 Dependencies

  • Run npm audit and update regularly; commit the lockfile
  • Fewer packages, from trusted maintainers
  • Third-party CDN scripts: add Subresource Integrity (integrity="sha384-…")

✅ Input and compliance

  • Validate on the client for UX, always again on the server
  • HTTPS everywhere
  • Personal data: consent, minimal collection, deletion (GDPR and similar laws)

XSS: the attacker's script runs on your site. CSRF: the attacker's site makes your browser send a request to your site with your cookies.

Hides the cookie from JavaScript (document.cookie), so XSS can't steal it. It is still sent with requests.

A CORS preflight: for non-simple cross-origin requests the browser asks the server which methods, headers and origins it allows.

Senior interview questions

Where should a single-page app store its auth token, and why?

Preferably not in the browser's JavaScript-readable storage at all: an HttpOnly, Secure, SameSite cookie (often set by a BFF) can't be read by XSS. If a bearer token must live in the client, keep it in memory, short-lived, with refresh via an HttpOnly cookie, and back it with a strict CSP.

How would you introduce a CSP to a large existing app without breaking it?

Start with Content-Security-Policy-Report-Only and a report endpoint, inventory sources, move inline scripts to files or nonces, then enforce gradually (per route or percentage), keeping reporting on to catch regressions.

4.2 Content Security Policy: strict, not allowlist

Use a nonce- or hash-based policy with 'strict-dynamic' (web.dev Strict CSP):

Content-Security-Policy:
  script-src 'nonce-{RANDOM}' 'strict-dynamic';
  object-src 'none';
  base-uri 'none';
  • The nonce must be new for every response, ideally 128+ bits (web.dev).
  • 'strict-dynamic' lets a trusted script load the scripts it creates, so you do not allowlist every CDN. object-src 'none' disables plugins. base-uri 'none' blocks injected <base> tags (web.dev).
  • Static or SSG pages that cannot inject a nonce per response use hashes instead (web.dev).
  • Roll out with Content-Security-Policy-Report-Only first. <meta> tags do not support report-only, so prefer the header (web.dev).
  • Reporting: modern report-to with a Reporting-Endpoints header, legacy report-uri (MDN, canonical). Browser support for each was not verified, so send both during transition unverified.

Why not an allowlist like script-src cdn.example.com? Any JSONP endpoint or old Angular copy on an allowed host can be used to bypass it (synthesis in the notes). Nonces also conflict with full-page CDN caching of HTML, so static sites use hashes (synthesis).

4.3 CSRF, SameSite and CORS

CSRF means another site makes the victim's browser send a cookie-authenticated, state-changing request. Example: evil.com auto-submits a form to bank.com/transfer, and the browser attaches bank cookies (OWASP CSRF).

Defences, in OWASP's order (OWASP CSRF):

  • Fetch Metadata is "the primary signal": reject cross-site non-safe requests using Sec-Fetch-Site. Origin checks are the fallback when the header is missing.
  • CSRF tokens: synchronizer token (stateful apps) or signed double-submit cookie (stateless apps). Naive double-submit is "documented for reference only".
  • Custom request header (for example X-CSRF-Token) for APIs, because it forces a CORS preflight; valid only if CORS allows only trusted origins.
  • SameSite is defence in depth. It "does not replace a proper CSRF defense". Lax still sends cookies on top-level GET navigations, so never change state on GET.
  • __Host- cookie prefix requires Secure, Path=/ and no Domain, which blocks subdomain overwrite.
  • XSS bypasses both tokens and SameSite.

Chrome treats cookies without a SameSite attribute as Lax by default since 2020 (web.dev, canonical).

CORS relaxes the same-origin policy for reading responses. It is not CSRF protection, because simple requests are sent without a preflight (MDN CORS).

4.4 Clickjacking, iframes and postMessage
  • Stop others framing you with CSP frame-ancestors (preferred) plus X-Frame-Options: DENY for old browsers (OWASP Headers).
  • When you frame others, use sandbox: the content becomes a unique origin with scripts and forms off; add back only the tokens you need (OWASP HTML5). Never combine allow-scripts and allow-same-origin on a same-origin iframe, because the framed script can remove its own sandbox (synthesis).
  • postMessage: pass an exact targetOrigin, not *. Match event.origin exactly; indexOf(".owasp.org") is insecure because owasp.org.attacker.com matches. Never eval the data; use textContent (OWASP HTML5).
  • Reverse tabnabbing: use rel="noopener noreferrer" and noopener,noreferrer in window.open (OWASP HTML5).

More rules from RFC 10017: the implicit grant is discouraged; refresh tokens for browser clients must be rotated on every use or sender-constrained; DPoP binds tokens to a browser-held key; no shared client secrets in browser apps; and PKCE does not stop an XSS attacker who starts a fresh flow (IETF). OWASP adds: "Do not store session identifiers in local storage" (OWASP HTML5).

Analogy. The BFF is a hotel concierge who keeps your valuables (tokens) in the safe and gives you a key card (cookie) that only works at the front desk.

BFF flow (synthesis): SPA hits /bff/login → BFF redirects to the identity provider with code + PKCE + state → provider returns the code to the BFF → BFF swaps it for tokens → BFF sets __Host-sid=...; Secure; HttpOnly; SameSite=Lax; Path=/ → SPA calls /bff/api/* and the BFF attaches the token. Because auth is now cookie-based, add CSRF defence.

Storage trade-off (synthesis):

Key nuance: HttpOnly does not make XSS harmless. It only stops token theft. Preventing XSS is still job number one.

JWT pitfalls to name: alg: none, algorithm confusion, not checking iss/aud/exp, tokens that cannot be revoked, secrets in the Base64 payload (OWASP JWT, canonical). Passkeys (WebAuthn) are bound to the site's origin, so they resist phishing, and the private key never leaves the device (MDN, canonical). Session hygiene (synthesis): 5–15 minute access tokens, rotated refresh tokens, server-side logout, and Clear-Site-Data on logout (cite MDN before using).

4.7 Supply chain, secrets and other traps

Supply chain is now OWASP #3 (A03:2025) (OWASP). In September 2025, a phishing email posing as npm support led a maintainer to reset 2FA on a fake page; trojanised versions of about 18 packages, including chalk and debug, were live for about two hours (CyberProof; Recorded Future, search-snippet level). Shai-Hulud was described as the first self-spreading npm worm: it stole tokens and republished infected versions of the victim's other packages (Cymulate). Package counts conflict across vendors (187 vs 500+; 25,000+ repos for version 2.0), so do not quote one number as fact unverified. GitHub's response plan includes mandatory 2FA for local publish, granular tokens with a maximum 7-day life, and trusted publishing via OIDC from CI (GitHub blog). Which of these are enforced as of November 2026 is unconfirmed.

Controls:

  • Commit the lockfile and install with npm ci; run audits (Dependabot, Renovate); restrict install scripts; check provenance (OWASP NPM, canonical).
  • A cooldown (do not auto-adopt versions younger than a few days), short-lived CI tokens, CSP connect-src to limit where injected code can send data, and an SBOM (synthesis).
  • No secrets in bundles. Anything in a frontend bundle is public, including NEXT_PUBLIC_/VITE_ env vars (notes; OAuth secret rule from RFC 10017).
  • Client validation is UX only; the server must validate (OWASP, canonical).
  • Prototype pollution: a naive deep-merge of {"__proto__": {"isAdmin": true}} sets a property on every object. Reject __proto__/constructor/prototype keys, use Object.create(null) or Map, validate with a schema (OWASP, canonical).
  • Open redirect: /login?next=https://evil.com. Allow only relative paths or an allowlist, parsed with new URL() (OWASP, canonical).
  • Client-side access control is UX only (hide buttons); every API must enforce authorisation (A01).
Architect's one-page security baseline

Framework escaping + lint bans on escape hatches · DOMPurify or setHTML inside one Trusted Types policy · strict nonce/hash CSP, report-only first · BFF + __Host- HttpOnly Secure SameSite=Lax cookie · Fetch Metadata + CSRF token · explicit CORS allowlist · header set at the CDN · SRI on versioned CDN scripts · lockfile, cooldown, provenance · passkeys · server-side validation and rate limits · open-redirect allowlist · CSP reports wired to monitoring.

Key takeaways
  • XSS is the root problem: it defeats CSRF tokens, SameSite and every token storage choice.
  • Strict CSP + Trusted Types (Baseline 2026) make dangerous sinks fail closed.
  • CORS controls reading, not sending. It is not CSRF protection.
  • RFC 10017: BFF is the strongest pattern; keep tokens out of the browser.
  • Supply chain is now a top-3 risk. Treat CI and npm tokens as crown jewels.

Interview questions with model answers

React escapes by default. Are we safe from XSS?

No. Escape hatches like dangerouslySetInnerHTML, user URLs in href, SSR-injected JSON state that does not escape <, third-party scripts, and DOM code outside React all remain. React 19 blocks javascript: URLs, but we still need URL validation, a sanitiser, strict CSP and Trusted Types.

Where should a SPA store its access token?

Ideally not in the browser. RFC 10017 recommends a BFF with an HttpOnly __Host- cookie. If a pure SPA is unavoidable: Authorization Code + PKCE, access token in memory, refresh token rotated or DPoP-bound, never localStorage for long-lived tokens, and strict CSP, because XSS defeats every storage choice.

Explain CSRF vs XSS.

CSRF uses the browser's automatic cookies from another site to send a request; it cannot read anything. XSS runs code inside your origin and can do anything the user can. Fix XSS first, because CSRF tokens do not help against XSS.

Does CORS protect my API?

No. It only relaxes the same-origin policy for reading. The server still needs authentication, authorisation and CSRF defence. A misconfigured CORS policy (reflected origin + credentials) is itself a vulnerability.

Design security for user-generated rich-text comments.

Store raw. Sanitise on render with DOMPurify or setHTML inside one Trusted Types policy. Strict nonce CSP. Links get a scheme allowlist and rel="noopener noreferrer nofollow ugc". Images through a proxy. Uploads served from a separate sandbox domain with nosniff.

How do you embed a third-party widget safely?

A sandboxed iframe on another origin, postMessage with exact origin checks and schema-validated messages, a CSP frame-src allowlist and Permissions-Policy to deny features. For third-party scripts, SRI if versioned, otherwise isolate them.

How would you harden our build pipeline?

Lockfile + npm ci, install scripts off by default, a cooldown on new versions, provenance and trusted publishing, short-lived CI tokens, dependency scanning, no secrets in client env vars, and source maps uploaded privately to the error tracker instead of being public.

E Real examples and use cases

British Airways 2018

one changed script skimmed card details

Illustrates: The basics; 4.6 Security headers and SRI

What Attackers changed a JavaScript file on BA's own site. The code was built for BA's payment page and sent card details to an attacker's domain.

Why No integrity check on the script, weak access controls (the regulator found no MFA on at least 13 critical applications), and nothing watching for script changes.

Result 429,612 customers and staff affected, with card numbers and CVVs for about 244,000. The attack ran from 22 Jun 2018, and BA learned of it from a third party on 5 Sep 2018. The UK regulator (ICO) fined BA £20m in Oct 2020, down from £183m proposed.

Lesson Start a security answer with a cost: one changed script cost £20m. SRI, a strict CSP connect-src and an isolated payment page each target this attack.

Source: TechCrunch, Oct 2020; Bird & Bird See it: The ICO penalty notice on ico.org.uk (search "British Airways penalty notice"): the £20m figure and the timeline. RiskIQ's 2018 write-up showed the changed script next to the original, but the page may have moved (not verified).

polyfill.io 2024

a sold CDN domain attacked 100K+ sites

Illustrates: 4.7 Supply chain, secrets and other traps; 4.6 SRI

What In Feb 2024 the cdn.polyfill.io domain passed to a new owner, the CDN company Funnull. The CDN then served changed JavaScript that sent some mobile visitors to scam and betting sites.

Why Sites loaded a live, unversioned third-party URL with no integrity hash.

Result Sansec disclosed it on 25 Jun 2024 and estimated 100K+ affected sites. Google stopped ads for e-commerce sites that used it. Cloudflare and Fastly set up safe mirrors.

Lesson Whoever owns a script's domain controls your page. Self-host the file, or pin a version with an integrity hash.

Source: Sansec; BleepingComputer See it: Sansec post: samples of the injected code (not verified).

Google 2016

proved most allowlist CSPs do not work

Illustrates: 4.2 Content Security Policy: strict, not allowlist

What Studied 26,011 unique CSP policies from Google's index of about 100 billion pages.

Why To check whether CSP protects real sites.

Result 94.72% of policies could be bypassed. 99.34% of hosts with CSP got no XSS protection from it. The authors proposed 'strict-dynamic'.

Lesson Strict CSP (nonce + 'strict-dynamic') is backed by measurement, not opinion.

Source: Google Research paper page; PDF See it: the PDF: result tables of bypass rates and the most-allowlisted domains (not verified).

Google 2019 onwards

Trusted Types ended DOM XSS in migrated apps

Illustrates: 4.1 XSS; 4.2 CSP (the Trusted Types bridge)

What Moved apps to Trusted Types, which block strings from reaching dangerous DOM sinks. Gmail got it in Jan 2024.

Why Before this, DOM XSS was more than 50% of the XSS reported to Google's bug bounty (secondary source).

Result Google reported zero DOM XSS in migrated apps since 2019. The rollout to Docs, Sheets and other editors was paused in Apr 2023 to check performance and quality.

Lesson Roll out product by product with a report-only phase. Even Google paused.

Source: PortSwigger Daily Swig; Workspace Updates, Feb 2023; Workspace Updates, Jan 2024 See it: Chrome Trusted Types guide: code and the error you get when a string hits a sink.

TweetDeck 2014

one missed escaping path

Illustrates: 4.1 XSS: attacker data treated as code

What A heart character made TweetDeck's emoji replacement skip HTML escaping. A tweet with a script in it ran in readers' TweetDeck and retweeted itself.

Why DOM-based XSS. One rendering step went around the normal escaping path and wrote to an HTML sink.

Result The tweet was retweeted "tens of thousands" of times. TweetDeck went offline for about an hour. (The popular "80,000+" figure was not found in any source.)

Lesson One missed path is enough. Put all sanitising in one place and lint-ban escape hatches.

Source: NPR; Sucuri See it: Sucuri post: the bug explained with the tweet's markup (not verified).

Okta 2023

session tokens leaked through HAR files

Illustrates: 4.5 Authentication and tokens in SPAs

What An attacker got into Okta's support system. Customers had uploaded HAR files (browser network recordings), and these held live session tokens. The attacker used them against 1Password, BeyondTrust and Cloudflare.

Why A HAR file saves cookies and Authorization headers in plain text.

Result 134 customers had files accessed, less than 1% of Okta's customers. Okta bound admin session tokens to network location and told customers to clean HAR files.

Lesson MFA protects the login, not the session after it. Never attach a raw HAR file to a ticket.

Source: Okta root cause; Krebs See it: Okta root cause post: the timeline (not verified).

CircleCI 2023

a stolen session cookie got past MFA

Illustrates: 4.5 Authentication and tokens in SPAs

What Malware on an engineer's laptop stole an SSO session cookie that was already backed by 2FA. Attackers logged in as the engineer without MFA.

Why A valid session cookie works like a key and was not bound to the device.

Result CircleCI rotated GitHub and Bitbucket tokens, told all customers to rotate their secrets, and added step-up login for staff with production access.

Lesson Use short-lived, device-bound sessions, and keep tokens server-side where you can (a BFF).

Source: CircleCI incident report; BleepingComputer See it: CircleCI report: the timeline section (not verified).

chalk, debug and Shai-Hulud 2025

phishing, then a self-spreading worm

Illustrates: 4.7 Supply chain, secrets and other traps

What A maintainer was phished by a fake npm-support email. Bad versions of chalk, debug and others went live and targeted crypto transactions in the browser. Days later the Shai-Hulud worm stole npm and GitHub tokens and republished infected versions of its victims' other packages.

Why Long-lived publish tokens and MFA that can be phished.

Result chalk had about 300M and debug about 358M weekly downloads. CISA said more than 500 packages were compromised (BleepingComputer counted 187).

Lesson Use phishing-resistant MFA, short-lived tokens, trusted publishing, lockfiles with npm ci, and a cooldown before you adopt new versions.

Source: CISA alert, Sep 2025; CERT/CC VU#534320; BleepingComputer See it: FortiGuard report: infection-chain diagram (not verified).

ING Direct and others 2008

CSRF moved real money

Illustrates: 4.3 CSRF, SameSite and CORS

What Princeton researchers found CSRF on ING Direct, YouTube, MetaFilter and the New York Times site. On ING Direct an attacker could open accounts in the victim's name and move the victim's money.

Why Requests that changed data trusted the browser's cookies alone, with no token and no origin check.

Result ING and MetaFilter fixed it; MetaFilter did it in under two days. The NYTimes status is disputed.

Lesson CSRF is common and easy to fix. SameSite=Lax as the browser default (2020) now blocks much of it.

Source: Princeton CITP blog; The Register See it: CITP post: the list of four sites and a link to the paper with an attack flow (not verified).

Twitter 2009

"Don't Click" made clickjacking real

Illustrates: 4.4 Clickjacking, iframes and postMessage

What A page showed a "Don't click" button. An invisible, pre-filled Twitter iframe sat over it. One click posted the same link to the clicker's feed.

Why Any site could frame Twitter, and the status form accepted pre-filled text.

Result It spread widely. Twitter's first fix was "two lines of JavaScript" to stop framing, and attackers got around it.

Lesson A JavaScript defence inside the page can be beaten by the page that frames it. Use frame-ancestors or X-Frame-Options headers.

Source: The Register, Feb 2009; Chris Shiflett See it: Shiflett post: the overlay technique explained (not verified).

Testing

🌱 In plain words

Tests are like checks on a car. Unit tests check each part on the bench (the brakes work). Integration tests check parts work together (pressing the pedal stops the wheels). End-to-end tests are a real test drive. You do many bench checks because they're quick, and a few test drives because they're slow but prove the whole car works.

Words to know

Assertion
The line that checks a result: expect(total).toBe(30).
Mock
A fake version of something (like an API) so the test is fast and predictable.
Coverage
How much of the code the tests run. High coverage doesn't mean good tests.
Flaky test
A test that sometimes passes and sometimes fails without any code change.
CI
Continuous integration: a server runs the tests on every change.

Tests let you change code without fear. A good frontend test suite catches broken logic, broken UI and broken user journeys, and runs on every pull request before anything reaches users.

5.2 Test like a user

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("shows an error when the email is empty", async () => {
  render(<SignupForm />);
  await userEvent.click(screen.getByRole("button", { name: /sign up/i }));
  expect(screen.getByText(/email is required/i)).toBeInTheDocument();
});

Do

  • Find elements by role and label, as users and screen readers do
  • Test behaviour: what the user sees and can do
  • Mock the network at the edge (MSW), not your own modules
  • One clear reason to fail per test

Don't

  • Test internal state or private functions
  • Rely on CSS classes or deep DOM paths
  • Use fixed sleep waits in E2E: wait for an element
  • Chase 100% coverage for its own sake

5.3 Beyond functional tests

🔁 TDD

Write a failing test, make it pass, then refactor: red → green → refactor.

🅰️ A/B testing

Show two versions to different users and compare a metric (sign-ups, clicks). It tests the product, not the code.

⚡ Performance tests

Lighthouse CI with budgets: fail the build if bundle size or LCP gets worse.

♿ Accessibility tests

axe-core in unit or E2E tests catches missing labels, low contrast and bad ARIA.

🔒 Security tests

npm audit, dependency scanners and scanning tools like OWASP ZAP.

🤖 CI

Run lint, type check, unit and integration tests on every PR; E2E on the main flows before deploy.

TrapFlaky E2E tests (pass sometimes, fail sometimes) teach the team to ignore failures. Keep E2E few, wait on conditions rather than time, and give each test its own clean data.

Q Flashcards

Why have many unit tests but few E2E tests?

Unit tests are fast and pinpoint the bug; E2E tests are slow and flakier but prove whole journeys work. Use each where it pays off.

Best query in React Testing Library?

getByRole with an accessible name, because it matches how users and assistive tech find things.

What is MSW for?

Mock Service Worker intercepts network requests in tests (and the browser), so components run their real fetch code against fake responses.

A/B test vs unit test?

A unit test checks the code is correct. An A/B test checks which version users prefer, measured by a metric.

Senior interview questions

The E2E suite takes 50 minutes and fails randomly. What do you do?

Measure which tests flake and why (timing waits, shared data, order dependence). Fix waits to be condition-based, isolate test data, run in parallel shards, move logic checks down to integration tests, and keep E2E for the few critical journeys. Quarantine flaky tests with an owner and a deadline.

How do you test a component library used by 20 teams?

Unit and interaction tests per component, accessibility checks with axe, visual regression on stories, type checks on the public API, and semantic versioning with changelogs so consuming teams can upgrade safely.

Flaky tests: the trust killer

Google reported that about 1.5% of all test runs were flaky and almost 16% of tests showed some flakiness. These are 2016 numbers: one is a share of runs, the other a share of tests (Google Testing Blog).

Policy (synthesis): quarantine a flaky test within a day, give it an owner and a 7-day deadline, delete it if not fixed. Allow at most one automatic retry, and report "passed on retry" as flaky, not green.

Coverage, TDD and BDD
  • Coverage is a smoke alarm, not a target. 70–80% line coverage on business logic is a common floor; 100% rewards tests with no assertions. Better signals: branch coverage on critical modules, mutation testing (Stryker), and a regression test for every production bug. These figures are common practice, not sourced BK.
  • TDD (red → green → refactor) fits pure logic, reducers, validators and bug fixes. BDD (Given/When/Then) helps only when product people really read the scenarios (synthesis).
Testing in CI/CD and in production

Pipeline pattern (synthesis):

  1. On commit: lint, typecheck, tests for changed files only (Nx or Turborepo affected graph).
  2. On PR: full Vitest suite, Storybook a11y and interaction tests, visual diffs, Pact consumer tests, Lighthouse CI budgets, bundle-size check, a Playwright smoke set of 5–15 journeys against a preview deploy. Target: feedback under about 10 minutes.
  3. On merge: full Playwright suite sharded, Pact provider verification, deploy behind a flag.
  4. After deploy: synthetic checks, RUM and error-rate watch, automatic rollback if the SLO burns.

Feature flags and A/B tests are testing in production. web.dev advises assigning experiment groups on the server, because client-side A/B tools often block rendering and hurt LCP. Tag every deploy with a version, because HTTP, service worker and CDN caches keep old code running (web.dev). A rollout ladder (staff → 1% → 5% → 25% → 50% → 100%) compares errors, INP, LCP and business KPIs at each step (synthesis). Flag types and lifetimes come from Fowler: release (days–weeks), experiment, ops kill switch, permission (years) (Fowler, Feature Toggles). Test both flag states in CI. Delete release flags after rollout.

Key takeaways
  • Choose the test shape from where your bugs come from, not from a percentage.
  • Default late-2026 stack: Vitest + Testing Library + MSW + Playwright + Storybook/Vitest + Chromatic + Pact.
  • Flakiness destroys trust. Measure it, quarantine fast, fix causes.
  • Coverage shows what is untested, not what is tested well.
  • Production testing (flags, staged rollout, RUM) adds to pre-production testing; it never replaces it.

Interview questions with model answers

Design a testing strategy for a large React app with 10 teams.

Types and lint everywhere. Trophy shape: most tests are component and integration tests with Vitest, Testing Library and MSW, or Storybook play functions in Browser Mode. Visual diffs on the design system. Pact between the frontend or BFF and the APIs. 10–20 Playwright journeys owned by teams via CODEOWNERS. Affected-only runs. PR feedback under 10 minutes. A flaky-test quarantine policy. I track flaky rate, PR time and escaped defects.

Unit vs integration: what is the right ratio?

First I ask what they mean by "unit": solitary or sociable. Then I pick the ratio from where past bugs came from. I look at the last 20 incidents and add tests at that layer.

Our E2E suite is flaky and takes 40 minutes.

Measure flake rate per test. Quarantine flaky ones. Replace sleeps with auto-waiting. Isolate data. Mock third parties. Push checks down to component tests. Shard. Keep only critical journeys in the PR gate and run the rest nightly.

Is 100% coverage a good goal?

No. It rewards tests with no real assertions and tests of implementation details. I set a floor for core logic and use mutation testing and regression tests for bugs.

How do feature flags change testing?

We test both flag states in CI, roll out gradually while watching RUM, use the flag as a kill switch, and delete it after rollout. And we assign experiment groups on the server so A/B tests do not hurt LCP.

Performance

🌱 In plain words

A web page is like a restaurant meal. TTFB is how long until the waiter shows up, FCP is when the bread arrives, LCP is when the main dish lands, CLS is the table wobbling and your plate sliding, and INP is how quickly the waiter responds when you wave. Performance work makes every one of those faster and steadier.

Words to know

Bundle
The JavaScript file(s) your build tool produces for the browser.
Main thread
The single thread where the browser runs your JavaScript and draws the page; if it's busy, taps wait.
Render
Turning HTML and CSS into pixels on the screen.
Lazy loading
Loading something only when it's about to be needed.
CDN
Servers around the world that keep copies of your files close to users.

A slow page loses users. Performance work means measuring first, then cutting what the browser has to download, run and render before the user sees and can use the page.

Keep the main thread free (INP)

  • Break long tasks (over 50 ms) into smaller ones
  • Debounce and throttle input and scroll handlers
  • Virtualize long lists: render only visible rows
  • Move heavy work to a Web Worker
  • Avoid needless re-renders (memoization)

Common slowdowns

  • Huge JS bundles on first load
  • Third-party tags (chat, analytics, ads)
  • Layout thrashing: reading then writing layout in a loop
  • Images without sizes; ads pushing content down
  • Client-side rendering everything when SSR or static would do
TipRendering strategy matters: SSR or static generation sends ready HTML, so content shows sooner than pure client-side rendering. Hydration then makes it interactive, at a JS cost.

Q Flashcards

Good thresholds for LCP, INP, CLS?

LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1, at the 75th percentile of real users.

preload vs prefetch?

preload: needed for this page, fetch now with high priority. prefetch: probably needed for the next page, fetch when idle.

Main cause of CLS?

Content without reserved space: images and embeds without dimensions, late ads and banners, web fonts swapping in.

What is tree shaking?

The bundler removes exports that nothing imports, which needs ES modules (import/export).

Why virtualize a list of 10,000 rows?

Rendering all of them makes a huge DOM; virtualization renders only the rows on screen and swaps them as you scroll.

Senior interview questions

LCP is fine in the lab but poor in the field. Why might that be?

Lab tests use one fast device and network with a warm setup; real users have slower phones and networks, cold caches, consent banners, personalised content, different LCP elements, and geographies far from your CDN. Segment field data by device, country and page to find the cause.

Route-based code splitting, a bundle analyzer in CI with per-route size budgets that fail the build, review of new dependencies, and lazy loading of heavy features behind interaction.

The main thread and long tasks. A long task is any main-thread task over 50 ms. While it runs, the browser cannot respond to input (web.dev long tasks). The event loop takes one task, runs all microtasks, then may render; rendering cannot happen in the middle of a task (BK, MDN event loop).

Analogy (from the notes): the main thread is a single-lane road. Each task is a truck. A user's click is an ambulance stuck behind the truck. scheduler.yield() makes each truck pull over regularly.

Yielding. scheduler.yield() resolves in a new task, and its continuation is prioritised ahead of other queued tasks. Support: Chrome/Edge 129, Firefox 142, not Safari. Fall back to setTimeout(r, 0) (yields without priority; after 5 nested calls a 5 ms minimum applies) or scheduler-polyfill. isInputPending() is no longer recommended (web.dev long tasks). requestIdleCallback, requestAnimationFrame, scheduler.postTask() and the Long Animation Frames (LoAF) API (Chrome 123+, the main tool for INP attribution in RUM) are BK; check Safari support on caniuse.

Fix INP in phase order (synthesis): input delay → cut long tasks at startup (hydration, third parties); processing → paint the visual response first, then yield and do the rest; presentation → smaller DOM, no layout thrashing, smaller re-renders.

Rendering architectures: choose per route, not per app

Facts from web.dev Rendering on the Web: CSR delays FCP and worsens TBT/INP as JS grows. SSR gives fast FCP but TTFB can rise. Static rendering gives consistently fast TTFB but needs every URL ahead of time. Streaming SSR sends HTML in chunks. Hydration "can hurt badly, since the page looks ready before it responds" and is "one app for the price of two". Google's advice: "Consider server-side rendering or static rendering over a full rehydration approach", and mixing patterns per page is fine.

  • ISR (Next.js): export const revalidate = 60; after the window, the next request still gets the stale page while regeneration runs in the background; on-demand with revalidatePath / revalidateTag; if regeneration fails, the last good page stays. Multi-instance deployments need a shared cache handler (Next.js ISR).
  • Islands: mostly static HTML with small interactive islands that hydrate on their own (Astro, Fresh, Marko). Islands cannot share state directly. The "80%+ less JS" claim for Astro docs sites is a vendor claim (patterns.dev).
  • Resumability (Qwik): no hydration. The server serialises listeners and state into HTML, and a tiny global listener downloads a handler only when its event fires. Code must be serialisable (Qwik).
  • React Server Components: render on the server or at build time; server-only libraries are not in the bundle; interactivity needs 'use client'; async components with <Suspense> stream. Stable in React 19, but bundler APIs are not semver (React).

Blockers: unload listeners (use pagehide), Cache-Control: no-store on HTML, open connections, a non-null window.opener. Detect restores with pageshow and event.persisted (web.dev bfcache). Interview questions with model answers

Our LCP is 4 s on mobile. How do you fix it?

Check field p75 on mobile and find the LCP element. Split the time into TTFB, load delay, load duration and render delay; the healthy split is about 40/10/40/10. High TTFB: CDN, cache HTML with SSG or ISR, streaming. Load delay: put the image in the HTML, fetchpriority="high", never lazy-load, preload if it is a CSS background. Load duration: AVIF or WebP with srcset. Render delay: remove render-blocking CSS and JS, inline critical CSS. Then add a CI budget.

What replaced FID and why?

INP, on 12 March 2024. FID measured only the input delay of the first interaction. INP measures all clicks, taps and key presses, including processing and presentation time. Good is 200 ms or less at p75.

How do you improve INP?

Find slow interactions with RUM and LoAF attribution. Reduce input delay by cutting long tasks at startup (hydration, third parties). Reduce processing by painting first, then yielding with scheduler.yield(), and moving heavy work to workers. Reduce presentation delay with a smaller DOM, content-visibility, no layout thrashing and useTransition.

Pick rendering strategies for an e-commerce site.

Home and listing pages: ISR at the edge. Product page: ISR plus islands or client components for price, stock and cart, or streaming SSR with RSC for personalised parts. Checkout and account: SSR or CSR, never CDN-cached. Admin: a CSR SPA. I would explain that hydration cost is why I prefer islands or RSC.

Reflow vs repaint? What is layout thrashing?

Reflow recomputes geometry and then forces paint, so it is expensive. Repaint only changes pixels. Compositor-only changes (transform, opacity) skip both. Layout thrashing is interleaving DOM writes and reads, which forces a layout each time; fix it by batching reads, then writes.

How would you render 100,000 rows?

Paginate or virtualise with overscan, memoise rows, use stable keys, sort and filter in a worker for big data, or use content-visibility for simpler rows. I would mention the trade-offs for accessibility and find-in-page.

How do you stop performance regressing across 20 teams?

Budgets in CI per route bundle, RUM dashboards per template with alerts on p75, a third-party script review, a shared optimised component library, a performance champion per team, and an owner per SLO. Meta did this with per-product JS budgets checked on every merge request.

How do you make navigations instant?

Speculation Rules with moderate document rules, bfcache eligibility, a service-worker app shell, and View Transitions to make the change feel smooth.

Database and Caching

🌱 In plain words

Caching is like keeping groceries at home instead of going to the shop for every meal. The fridge (memory) is fastest but small, the cupboard (browser storage) holds more, the corner shop (CDN) is close by, and the big supermarket (origin server) has everything but is far away. The hard part is knowing when the milk at home has gone off: that's cache invalidation.

Words to know

Cache
A saved copy kept so you don't have to fetch or compute it again.
Stale
A cached copy that might be out of date.
TTL / max-age
How long a cached copy may be used before checking again.
Invalidation
Throwing away or refreshing a cached copy when the real data changes.
Origin
Here: the main server that has the real data.

The fastest request is the one you don't make. Frontends keep data in several places: in memory, in browser storage, in the HTTP cache and in a service worker. The design question is what to keep where, and for how long it can be trusted.

🔄 Server-state libraries

TanStack Query, SWR, RTK Query and Apollo Client cache responses by key, dedupe requests, retry, and refetch stale data. They implement stale-while-revalidate for you.

🧱 Normalization

Store each entity once by id (users: {"42": {...}}) and reference it from lists. Updating user 42 then updates every screen that shows them.

⚖️ Server state vs UI state

Server state (posts, orders) is owned by the backend and goes stale; UI state (open modal, input text) lives only in the client. Keep them in different places.

✨ Optimistic updates

Update the UI before the server replies (a like shows at once), then roll back if the request fails.

Q Flashcards

Where to store 50 MB of offline messages?

IndexedDB: asynchronous, large, stores objects. localStorage is too small and blocks the main thread.

no-cache vs no-store?

no-cache: store it but revalidate before using. no-store: don't store it at all.

What does a 304 mean?

Not Modified: the cached copy (matched by ETag or Last-Modified) is still valid, so no body is sent.

Why hash file names like app.3f9a.js?

So they can be cached for a year: any change gives a new name, which busts the cache automatically.

localStorage vs sessionStorage?

Same API; localStorage lasts until cleared and is shared across tabs of the origin; sessionStorage is per tab and gone when it closes.

Senior interview questions

A user updates their profile picture, but the old one keeps showing for an hour. Where would you look?

Every layer: the image URL probably didn't change while CDN or browser caches hold it with a long max-age. Fix by giving each upload a new URL (versioned or hashed), and invalidate client caches of the profile data after the mutation.

7.1 Browser storage: the basics

Cache busting = put a hash in the URL. The main HTML cannot be busted, so it must be no-cache. No HTTP mechanism deletes a stored response from intermediate caches; Clear-Site-Data: "cache" clears only the browser cache. Only managed caches (CDN purge, caches.delete) can be purged (MDN). Data-fetching caches. TanStack Query's defaults: data is stale at once (staleTime 0); inactive queries are garbage-collected after 5 minutes; stale queries refetch on mount, window focus and reconnect; failed queries retry 3 times with exponential backoff; structural sharing keeps unchanged references (TanStack Query). Library comparison (BK, docs not fetched): TanStack Query and SWR are document caches keyed by query key; RTK Query uses tag invalidation; Apollo and Relay use a normalised cache keyed by __typename:id, so one mutation updates every view, at the cost of complexity.

Invalidation strategies BK: time-based (TTL), event-based (after a mutation), versioned URLs, CDN tag purge, push-based (SSE/WebSocket says which keys changed), write-through (update the cache from the mutation response). Rule of thumb: immutable things get versioned URLs and infinite TTL; mutable things get short TTL plus revalidation. Never cache personalised responses at the edge without a per-user key BK.

Analogy (from the notes): server state is a library book. You borrowed it, it can go out of date, and the library owns it. Client state is your own notebook.

Decision rules BK:

  1. If it comes from the server, it is not your state. Cache it.
  2. If users should share or bookmark it, put it in the URL.
  3. Keep state as close to where it is used as possible.
  4. Add a global store only when three or more distant components read and write the same client state.
  5. Derive, do not duplicate.

Normalisation BK: store entities by id ({byId, allIds}), so one update fixes every view.

Optimistic updates with rollback (BK, the TanStack pattern): cancel in-flight queries for the key → snapshot the old data → write the expected result → on error restore the snapshot and show a message → on settle, refetch. Use client-generated UUIDs for new items. Use optimism for high-success, reversible actions (like, rename, reorder), not for payments.

Real example. Linear's client keeps an in-memory MobX object pool loaded from IndexedDB at startup; writes apply locally first and are queued as transactions; the server sends deltas back. This comes from secondary, reverse-engineered sources, not Linear's own docs (performance.dev; Convex).

Key takeaways
  • localStorage is small and synchronous; use IndexedDB or OPFS for real data and HttpOnly cookies for tokens.
  • Storage is best-effort and evictable, and Safari wipes script storage after 7 idle days for non-installed sites.
  • Hashed assets: one year + immutable. HTML: no-cache. You cannot recall a long cache from intermediate caches.
  • Split server, URL, form and UI state. Global stores are not API caches.

Interview questions with model answers

localStorage, IndexedDB or cookies for an auth token?

An HttpOnly Secure SameSite cookie. Anything JavaScript can read is exposed to XSS.

no-cache vs no-store?

no-cache stores the response but revalidates it every time, often with a cheap 304. no-store never stores it and also blocks bfcache. I use no-store only for secrets.

We deployed new hashed JS but users still see the old app. Why?

Probably the HTML is cached too long, or an old service worker serves precached HTML. Fix: HTML and sw.js with no-cache, versioned SW caches, and an update prompt that calls skipWaiting.

How do you invalidate client data after a mutation?

Update the cache from the mutation response, or invalidate the affected query keys or tags. A normalised cache updates every view of the entity. For fast UX, an optimistic update with snapshot rollback.

Where should filter state live in a dashboard?

In URL search params, so it is shareable and the back button works. Server data goes in the query cache, keyed by those params.

When do you need Redux?

Only for complex shared client logic that many distant components read and write, with big teams that want devtools and strict event flows. Not for caching API data; that belongs in a server-state library.

Logging and Monitoring

🌱 In plain words

Monitoring is like a car's dashboard and black box. The dashboard (metrics) shows speed and fuel right now; warning lights (alerts) tell you when something is wrong; the black box (logs and error reports) tells you exactly what happened after a crash. Without them, you only learn something broke when users complain, or quietly leave.

Words to know

Log
A recorded message about something that happened in the app.
Metric
A number tracked over time, like errors per minute or LCP.
Stack trace
The list of function calls that led to an error, used to find the bug.
RUM
Real User Monitoring: measuring performance on real users' devices.
Alert
An automatic message to the team when a metric crosses a limit.

After release, your code runs on thousands of devices you'll never see. Logging and monitoring tell you what broke, for whom, and how fast the app really is, often before users complain.

8.1 What to collect

💥 Errors

Uncaught exceptions, rejected promises, failed API calls, with stack trace, browser, app version and user steps.

⏱️ Performance (RUM)

Real-user LCP, INP, CLS, TTFB, by page, device and country.

📊 Usage events

Page views, clicks, funnel steps (cart → checkout → paid).

🌐 Network

Slow or failing endpoints, status codes, timeouts.

The basics: why the frontend is different

Backend code runs on your servers. Frontend code runs on thousands of devices, browsers, extensions and networks, and the tab can close at any moment (synthesis in the notes). Google's SRE Workbook says instrumentation in the page's JavaScript best captures the real user experience, and recommends measuring on the client where possible because it is closer to the user (Google SRE Workbook).

Analogy (from the notes): backend monitoring is a CCTV camera in your own shop. Frontend monitoring is asking thousands of delivery drivers to phone in, on bad mobile signal, before they hang up.

Error tracking

Four capture points (BK; check React and MDN docs):

  1. window.addEventListener('error', …) for uncaught errors. Cross-origin scripts show only "Script error." unless loaded with crossorigin="anonymous" and a CORS header.
  2. unhandledrejection for promise rejections nobody handled.
  3. React Error Boundaries for render errors: show a fallback and report. They do not catch errors in event handlers or async code.
  4. Wrappers around fetch/XHR for failed API calls (status, endpoint, latency, trace ID).

Source maps BK: upload them to the error tool at build time, tagged with the release, and do not serve them publicly.

Every event needs BK: release version, route, browser and OS, device class, hashed user or session ID, active feature flags, breadcrumbs (last clicks, navigations, requests), and a trace ID to join backend traces (W3C traceparent).

Sampling defaults in Sentry. Error sampleRate defaults to 1 (send all). tracesSampleRate is unset, so no performance traces are sent until you set it; start low. tracesSampler can set rates per route (Sentry Sampling).

OpenTelemetry in the browser is "experimental and mostly unspecified"; use BatchSpanProcessor for efficient export (OpenTelemetry).

Logging practice

Levels BK: debug (dev only, stripped from production), info (key lifecycle events, sampled), warn (recovered problems), error (user-facing failures, always sent), fatal (crash or white screen).

Structured shape BK: {ts, level, msg, event, release, route, sessionId(hashed), traceId, browser, device, flags, context}. Never send string-only logs you cannot query.

Sampling BK: keep 100% of errors (with dedupe per fingerprint), 1–10% of performance traces, 10% or less of sessions for replay. Sample per session, not per event, so one user's story stays whole.

Batching BK: buffer in memory, flush every N events or T seconds and on visibilitychange, retry with backoff, and drop data when offline or the queue is full, so logging never hurts the app. The often-quoted ~64 KB payload limit for sendBeacon/keepalive is unverified.

Session replay (Sentry Session Replay): replaysSessionSampleRate starts at 0.1 (10%); replaysOnErrorSampleRate is recommended at 1.0. Defaults mask all text, block all media and mask inputs. Replay rebuilds the DOM, not a real video; compression runs in a Web Worker; in error mode it keeps the last 60 seconds in memory and uploads only if an error happens. It can be lazy-loaded.

PII checklist BK: no emails, names, tokens or card numbers in messages or URLs; scrub query strings; redact in beforeSend; hash user IDs; mask replay by default; honour consent (GDPR, India's DPDP Act); set retention limits; keep data in the right region.

SLIs, SLOs, error budgets and alerts

From the Google SRE Workbook (SRE Workbook):

  • SLI = good events ÷ valid events.
  • SLO = target for the SLI. Example: a 99.9% SLO over 4 weeks with 3 million requests allows about 3,000 failures; an outage with 1,500 errors uses half the budget.

Accessibility

🌱 In plain words

Accessibility is like adding ramps, lifts, braille signs and clear labels to a building: some people can't use the stairs, some can't see the signs. Online, some people use only a keyboard, some listen with a screen reader, some zoom in, some can't tell red from green. Good HTML is the ramp: it works for everyone, including you on a phone in bright sunlight.

Words to know

Screen reader
Software that reads the page aloud and lets blind users navigate by headings, links and form fields.
Semantic HTML
Using elements for their meaning: button for buttons, nav for navigation.
Focus
Which element receives keyboard input right now; shown by the focus ring.
ARIA
Attributes that tell assistive technology what custom elements are and what state they're in.
Contrast ratio
How different text colour is from its background; higher is easier to read.

Accessibility (a11y) means people can use your app however they use a computer: keyboard only, a screen reader, zoomed to 200%, with low vision or colour blindness, or with a shaky hand. It's good design, often a legal requirement, and it helps everyone.

9.1 WCAG and POUR

The Web Content Accessibility Guidelines (current version WCAG 2.2) have levels A, AA and AAA. Most laws and companies target AA. Every rule falls under four principles:

POUR
  • Perceivable: text alternatives, captions, contrast
  • Operable: keyboard, enough time, no seizure risks
  • Understandable: clear labels, predictable, helpful errors
  • Robust: valid markup that assistive tech can read

9.2 Semantic HTML first

<!-- ❌ looks like a button, but no keyboard, no role, no focus -->
<div class="btn" onclick="save()">Save</div>

<!-- ✅ focusable, Enter and Space work, announced as "Save, button" -->
<button type="button" onclick="save()">Save</button>

🏷️ Use the right element

  • <button> for actions, <a href> for navigation
  • Landmarks: header, nav, main, footer
  • One h1, headings in order
  • <label for> on every input

🖼️ Text alternatives

  • alt that says what the image means
  • alt="" for decorative images
  • Icon-only buttons need an accessible name (aria-label)
  • Captions for video, transcripts for audio
KeyThe first rule of ARIA: if a native HTML element does the job, use it. ARIA changes only what assistive tech is told; it adds no keyboard behaviour. "No ARIA is better than bad ARIA."

9.3 Keyboard and focus

Tab orderFollows the visual order; avoid positive tabindex.
Visible focusNever remove outlines without a clear replacement (:focus-visible).
Skip link"Skip to main content" as the first focusable item.
ModalsMove focus in, trap it inside, close on Escape, return focus to the opener.
Custom widgetsArrow keys for tabs, menus and listboxes, as in the ARIA Authoring Practices.

9.4 ARIA you'll actually use

AttributeUse
aria-label / aria-labelledbyGive a name when there's no visible text
aria-describedbyLink an input to its hint or error message
aria-expandedIs the accordion, menu or dropdown open?

role="dialog" + aria-modalMark a custom modal (or use the native <dialog>)

9.5 Seeing and testing

Do

  • Contrast at least 4.5:1 for normal text, 3:1 for large text and UI parts (AA)
  • Show meaning with text or icons too, not colour alone
  • Support 200% zoom and respect prefers-reduced-motion
  • Touch targets big enough to tap

Don't

  • Use placeholder text as the only label
  • Auto-play audio or moving content you can't pause
  • Rely only on automated checks: they miss many issues

🤖 Automated

axe DevTools, Lighthouse accessibility audit, eslint-plugin-jsx-a11y, axe in tests.

⌨️ Manual

Unplug the mouse and use the app with Tab, Enter, Space, Escape and arrows.

🔊 Screen readers

VoiceOver (Mac, iPhone), NVDA (Windows), TalkBack (Android).

Q Flashcards

What does POUR stand for?

Perceivable, Operable, Understandable, Robust: the four WCAG principles.

WCAG AA contrast for body text?

At least 4.5:1 (3:1 for large text and for UI components).

Why is <div onclick> a problem?

It isn't focusable, doesn't respond to Enter or Space, and isn't announced as a button. Use <button>.

Four focus rules for a modal?

Move focus into it, keep focus inside, close on Escape, return focus to the element that opened it.

How to announce "Saved" without moving focus?

Put the message in an aria-live="polite" region (or role="status").

Senior interview questions

In a single-page app, a screen-reader user clicks a link and hears nothing. Why, and how do you fix it?

Client-side routing swaps content without a page load, so assistive tech isn't told. After navigation, update the document title, move focus to the new page's main heading (or a wrapper with tabindex=-1), and optionally announce it in a live region.

How would you make accessibility scale across 15 product teams?

Ship accessible components in the shared design system, document patterns, add automated checks in CI, train teams, include a11y in design reviews and the definition of done, and run regular audits with real assistive-technology users.

WCAG 2.2: the basics

WCAG is organised under four principles, POUR: Perceivable, Operable, Understandable, Robust. Each success criterion has a level: A, AA or AAA (WCAG 2.2).

Analogy (from the notes): a building. Can you see the door sign (Perceivable)? Can you open the door (Operable)? Do you know which door goes where (Understandable)? Does the door work with your wheelchair, cane or guide dog (Robust)?

WCAG 2.2 became a W3C Recommendation on 5 October 2023. It removed 4.1.1 Parsing and added nine criteria (W3C). The A/AA ones that affect frontend code most:

CriterionLevelWhat to do
2.4.11 Focus Not Obscured (Min)AASticky headers and cookie bars must not fully hide focus; use scroll-padding-top
2.5.7 Dragging MovementsAAEvery drag has a click/tap or keyboard alternative
2.5.8 Target Size (Min)AATargets at least 24×24 CSS px or enough spacing; many teams choose 44px for touch
3.2.6 Consistent HelpAHelp appears in the same order on every page

The "what to do" column for 2.4.11, 2.5.7, 2.5.8 and 3.3.8 is a synthesis in the notes. WCAG 3.0 is still a Working Draft in late 2026 and W3C says it is "a few more years" away (W3C). AbilityNet's guess is Candidate Recommendation around Q4 2027 (third-party estimate, AbilityNet). Build to 2.2 AA.

Semantic HTML and ARIA

The APG says ARIA is like CSS for assistive technologies, and "a role is a promise": using a role commits you to building its behaviour. "ARIA roles do not cause browsers to provide keyboard behaviors or styling" (W3C APG). In 2026, pages with ARIA averaged 59.1 errors vs 42 without it. That is a correlation, not proof that ARIA causes errors (WebAIM Million).

Analogy (from the notes): HTML elements are furniture from a shop; they already work. ARIA is a label on a cardboard box saying "chair". The screen reader believes the label, but nobody can sit on the box until you build the chair (the JavaScript behaviour).

The five rules of ARIA (from W3C "Using ARIA"; wording not re-fetched, BK):

  1. Use a native element if one exists.
  2. Do not change native semantics unless you must.
  3. Every interactive ARIA control must work with a keyboard.
  4. Never put role="presentation" or aria-hidden="true" on a focusable element.
  5. Every interactive element needs an accessible name.

Accessible name order (simplified, BK): aria-labelledby > aria-label > native label (<label for>, alt, <legend>) > text content > title (last resort).

Headings and landmarks. 71.6% of screen reader users first navigate a long page by headings (WebAIM Screen Reader Survey #10). Use one <h1>, no skipped levels, and the landmarks <header>, <nav>, <main> (one), <aside>, <footer>, labelling repeats (<nav aria-label="Breadcrumb">) BK.

Live regions BK: role="status" / aria-live="polite" for toasts and result counts; role="alert" / assertive only for urgent errors. The region must already exist in the DOM before its text changes, or many screen readers stay silent.

<!-- Bad: no role, no name, no keyboard -->
<div class="btn" onclick="save()"><svg>…</svg></div>
<!-- Good: native button; Enter/Space work; aria-label gives the name -->
<button type="button" aria-label="Save draft"><svg aria-hidden="true">…</svg></button>
Keyboard and focus

The platform now does most of the hard work:

  • <dialog> + showModal() is Baseline since March 2022 (MDN). It puts the dialog in the top layer, makes the page behind it inert, closes on Esc and returns focus (behaviour as described in the notes).
  • Popover API is Baseline 2024 (Chrome/Edge 114, Firefox 125, Safari 17) (web.dev) for non-modal layers with light-dismiss. It does not make the page inert.
  • <dialog closedby="any"> (click-outside close) shipped in Chrome/Edge 134 and Firefox 141 but not Safari as of the 26.5 preview (web-features). Use JavaScript for click-outside until then.
  • inert on a background subtree removes focus, clicks and accessibility-tree exposure; it replaces hand-written focus traps BK.

Screen reader users rank misbehaving menus, tabs and dialogs 2nd and lack of keyboard access 5th among their biggest problems; CAPTCHA is 1st (WebAIM SR Survey #10).

Rules the app still owns (BK, teaching content):

  • Focus order follows DOM order. Never use positive tabindex. tabindex="0" adds a custom element to Tab order; -1 makes it focusable by script only.
  • SPA route change: update document.title, move focus to the new <h1 tabindex="-1">, optionally announce "Navigated to X" in a polite live region.
  • Roving tabindex for toolbars, tabs and radio groups: one Tab stop for the group, arrows move inside, active item tabindex="0", others -1. aria-activedescendant keeps DOM focus on the container; preferred for comboboxes. Analogy: one door into each office (Tab); inside, you walk between desks (arrows).
  • Skip link as the first focusable element, visible on focus, targeting <main id="main" tabindex="-1">.
  • Visible focus with :focus-visible; never outline: none without a replacement.

Forms, images, media and APG patterns

Forms checklist BK: a visible <label for> for every input (a placeholder is not a label); <fieldset> + <legend> for groups; required marked in text and with required; autocomplete tokens; on error aria-invalid="true" + aria-describedby, then focus an error summary or the first invalid field (the GOV.UK pattern, not fetched); never clear the user's input.

Alt text BK: informative → describe the purpose; decorative → alt=""; functional icon → describe the action ("Search"); complex chart → short alt plus a data table nearby; never "image of…". Media BK: captions, audio description, transcripts, no autoplay with sound, pause controls for anything moving more than 5 seconds.

APG Combobox contract (W3C APG Combobox): role="combobox" on the input; aria-expanded; aria-controls → a listbox of options; aria-autocomplete; aria-activedescendant while focus stays in the input; Down Arrow opens or moves in; Enter accepts; Escape closes; Alt+Down opens without moving focus. Tabs, menu button, disclosure and grid patterns are BK (APG pages not fetched). Key warnings: use menu/menuitem only for app-style action menus, not site navigation; use role="grid" only for interactive spreadsheet-like grids, and a plain <table> for read-only data.

Analogy (from the notes): the APG is a recipe book. If you claim to serve lasagne (a role), guests expect its layers (its keys).

Architect move (synthesis): do not let teams hand-build comboboxes. Ship one audited component in the design system, built on React Aria, Radix or Headless UI, and test it with screen readers once.

  2. Component tests with getByRole(..., {name}) plus vitest-axe; Storybook a11y addon on every story.
  3. @axe-core/playwright in CI on key pages and states; fail on new serious/critical violations with a baseline for old debt.
  4. Manual keyboard pass per feature.

Interview questions with model answers

Design an accessible autocomplete.

Label the input and give it role="combobox", aria-expanded, aria-controls and aria-autocomplete="list". Results are a listbox of options. Focus stays in the input; arrows move aria-activedescendant; Enter selects; Esc closes. A polite live region announces "5 suggestions" after the debounce, plus loading and empty states. It is one design-system component with Playwright keyboard tests, axe, and a manual NVDA and VoiceOver check.

Build an accessible modal.

Native <dialog> with showModal(). It gives the top layer, an inert background, Esc to close and focus return. I name it with aria-labelledby, put autofocus on the least destructive button, and lock background scroll. Click-outside close needs JavaScript until Safari ships closedby.

Focus is lost after route changes in our SPA. Fix it platform-wide.

A hook in the router shell sets document.title, focuses the new <h1 tabindex="-1">, and announces the page in one app-level polite live region. An E2E test checks document.activeElement after navigation.

How would you make 40 teams ship accessible UI?

Policy: WCAG 2.2 AA in the definition of done. Platform: an accessible design system with checked tokens and APG components, plus lint. Guardrails: axe in Storybook and Playwright with a CI gate on new violations. People: champions and screen reader training. Evidence: expert audits, user testing, an ACR. And I am honest that automation covers only about 30–57%.

When would you use ARIA?

Only when no native element exists (tabs, combobox, tree, live regions) or to connect relationships like aria-describedby. And I always add the keyboard behaviour the role promises.

Roving tabindex or aria-activedescendant?

Roving tabindex moves real focus; it is simpler and scrolls into view for free, so I use it for toolbars, tabs and radio groups. aria-activedescendant keeps focus on one element, so I use it for comboboxes and large virtual lists, but then I must scroll the active item into view myself.

Offline Support

🌱 In plain words

A service worker is like a personal assistant at your door. When you ask for something, the assistant checks the network for a fresh copy; if the line is down, they hand you the copy kept in the cupboard (cache). Notes you write while offline go into an outbox the assistant posts when the line comes back.

Words to know

Offline-first
Design where the app works from local data first and syncs with the server when it can.
Service worker
A background script that can intercept the page's network requests.
App shell
The minimal HTML, CSS and JS that draw the app's frame, cached so it opens instantly.
Sync
Sending local changes to the server and getting the latest back.
PWA
Progressive Web App: a website that can be installed and works offline.

Networks fail: in lifts, on trains, on cheap data plans. An app with offline support still opens, shows what it already has, lets users keep working, and syncs when the connection comes back. The tools: service workers, the Cache API, IndexedDB, and a web app manifest to make it a PWA.

10.1 Service workers

A service worker is a script that runs in the background, separate from the page, and sits between the page and the network: it can answer any request from a cache. It needs HTTPS (localhost is allowed for development).

InstallPre-cache the app shell: HTML, CSS, JS, icons

FetchIntercept every request and choose a strategy
// sw.js
self.addEventListener("install", (e) => {
  e.waitUntil(caches.open("shell-v2").then((c) => c.addAll(["/", "/app.css", "/app.js"])));
});
self.addEventListener("fetch", (e) => {
  e.respondWith(caches.match(e.request).then((hit) => hit || fetch(e.request)));
});

The basics: service worker lifecycle

A service worker is a script the browser runs between your page and the network. Facts from MDN Using Service Workers:

  • Register with navigator.serviceWorker.register("/sw.js", {scope: "/"}). HTTPS is required (localhost is allowed).
  • install: event.waitUntil() decides success; if it rejects, the new worker is thrown away.
  • A new version waits while the old one controls open pages; the very first worker activates immediately. skipWaiting() skips the wait; clients.claim() takes control of open pages.
  • activate: delete old caches and run migrations.
  • fetch: fires for every in-scope request; event.respondWith() supplies the response; clone responses before caching. Navigation preload starts the navigation request while the worker boots.

Keep activate short, because fetches queue during it, and remember the worker can be killed when idle (web.dev Offline Cookbook). Name caches with versions (v2) and delete old ones in activate (MDN).

Analogy (from the notes): offline-first is writing letters on a plane. You write freely (local DB), put them in the outbox, and they are posted when you land (sync). If two people edited the same shopping list, you need a rule to merge.

Detecting offline and updating safely BK
  • navigator.onLine and the online/offline events only say a network interface exists, not that your server is reachable ("lie-fi"). Confirm with a real request or heartbeat, and treat failed fetches as offline.

PWA installability and Background Sync

Chrome's install criteria: the user has interacted at least once and spent 30 s on the page; HTTPS; a manifest with name or short_name, 192 px and 512 px icons, start_url, and a display of fullscreen, standalone, minimal-ui or window-controls-overlay. The criteria page does not list a service worker as required (web.dev install criteria). Installed iOS PWAs get their own storage container and are exempt from Safari's 7-day eviction (web.dev).

Background Sync works in Chrome (since 49) and Edge (since 80) but not in Safari or Firefox (Firefox's vendor position is negative), and it is not Baseline. Periodic Background Sync is even less supported (caniuse; MDN). So every offline design needs a fallback: replay the queue on the online event, app start or visibilitychange.

The outbox pattern BK
  1. Write to the local DB and an outbox table with a client UUID and an idempotency key.
  2. Update the UI at once; the UI reads from the local DB (a live query), never waiting for the network.
  3. When online (Background Sync in Chromium; online, app start or focus elsewhere), replay in order with retries and exponential backoff.
  4. The server dedupes by idempotency key.
  5. Mark done and reconcile with the server response.

Workbox's BackgroundSyncPlugin / Queue implements this with a fallback replay on service-worker start (BK, verify).

Conflict resolution and sync engines

Figma rejected OT as too complex for a design tool. It uses a CRDT-inspired, server-authoritative, last-writer-wins per property model: edits to different properties never conflict, and same-property edits keep one value. Offline clients reconnect by downloading a fresh document, reapplying their edits, and opening a new WebSocket. Child order uses fractional indexing, and the server rejects updates that create cycles (Figma blog).

Linear uses a local-first style: IndexedDB as a real database, an in-memory MobX pool, local write → queued transaction → server → deltas to all clients (from secondary sources: performance.dev; Convex).

Local-first software (Ink & Switch, 2019) lists seven ideals: no spinners; not trapped on one device; network optional; seamless collaboration; the long now; security and privacy by default; user ownership. In a cloud app, the server is primary and the client is a cache; in local-first, the device is primary (Ink & Switch). CRDTs merge concurrent edits automatically, but simultaneous edits of the same property cannot merge meaningfully, history grows, and servers are still useful for discovery and backup (Ink & Switch).

Interview questions with model answers

Design an offline-capable notes app.

Requirements: create, edit and search notes offline; sync across devices; instant UI; no data loss; works on iOS. Storage: IndexedDB via Dexie with a notes table and an outbox, or SQLite WASM on OPFS in a worker if I need full-text search. The SW precaches the hashed shell; HTML is network-first with a fallback. I call persist() after the first saved note. Writes go to the local DB and outbox with a client UUID; the UI reads only from the local DB. Sync pushes the outbox (Background Sync in Chromium, online and app start elsewhere) and pulls deltas since a cursor. Conflicts: LWW per field for title and folder; a CRDT per note only if real-time co-editing is required; tombstones for deletes. Edge cases: quota full, Safari eviction (encourage install), schema migrations, clearing data on logout, one syncing tab via Web Locks. Metrics: sync lag, conflict rate, outbox failures.

How does Safari affect your offline design?

No Background Sync, and script storage is deleted after 7 days without interaction unless the PWA is installed. So the server is the backup, and I replay the queue on app open.

CRDT vs OT vs LWW?

LWW is simplest but loses one of two concurrent edits. OT needs a central server and complex transforms, like Google Docs. CRDTs merge without a central authority but cost memory and history. Figma chose server-authoritative LWW per property because design objects are not long text.

Users see an old version after we deploy. How do you handle SW updates?

Serve sw.js and HTML with no-cache, version the caches and delete old ones in activate, and show a "New version — Reload" prompt that calls skipWaiting, rather than swapping code silently.

Low Level Design (LLD)

🌱 In plain words

LLD is like being asked to design one really good kitchen tool, not the whole kitchen. You decide how people hold it (the props, its API), what it remembers (state), what happens if they use it wrongly (edge cases), and whether everyone can use it, including left-handed people (accessibility).

Words to know

Component
A reusable piece of UI, like a button or a search box.
Props
The inputs you pass into a component to configure it.
State
Data a component remembers that can change, like the text typed so far.
Edge case
An unusual situation: empty results, very long text, slow network.
Race condition
When the result depends on which of two things finishes first.

The LLD round asks you to design and usually code one component or feature so it is reusable, correct in edge cases, fast and accessible. The interviewer watches how you shape the API, manage state and handle what can go wrong.

ClarifyFeatures, inputs, devices, scale (10 items or 100,000?)

Good component API

  • Small, clear props with sensible defaults
  • Controlled and uncontrolled modes where useful
  • Callbacks for events (onChange, onSelect)
  • Render props or slots for custom looks

Warning signs

  • Dozens of boolean props
  • State copied from props and drifting out of sync
  • Fetching inside deep children

Two key patterns

Compound components. A parent (for example FlyOut) owns state and shares it through Context with child parts (FlyOut.Toggle, FlyOut.List, FlyOut.Item). Use the six beats: requirements → API/props → state → behaviour and edge cases → accessibility → performance.

1. Autocomplete / typeahead.

  • API: fetchSuggestions(query), minChars, debounceMs, renderItem, onSelect, controlled value.
  • State: query, results, highlightedIndex, status (idle / loading / error / empty).
  • Behaviour: debounce ~200–300 ms; cancel stale requests with AbortController or drop out-of-order responses by request id; cache per query (LRU Map); highlight the match.
  • A11y: the APG combobox contract (Module 9).
  • Performance: virtualise long lists; cache; prefetch popular queries.

2. Infinite scroll. IntersectionObserver on a sentinel (not scroll listeners); cursor-based fetching; an isLoading guard against double fetch; virtualise when the DOM grows; keep scroll position on back navigation; a "Load more" button fallback so the footer stays reachable by keyboard; announce new items politely.

3. Image carousel. Props images, autoPlay, interval, loop, controlled index. Render only current ± 1 slides and lazy-load the rest. Interview questions with model answers

Design a reusable Tabs component API.

A compound API: <Tabs value onValueChange defaultValue><Tabs.List><Tabs.Tab value="a"/></Tabs.List><Tabs.Panel value="a"/></Tabs>. State is in Context and controllable. It follows the APG tabs pattern with roving tabindex and arrow keys, forwards refs, spreads props, and ships unstyled behaviour under design-system styles.

Controlled or uncontrolled?

Both. If value is passed, the parent owns it; otherwise the component keeps internal state from defaultValue. I warn if it switches mode during its life.

How do you prevent "prop explosion"?

Move up the API ladder: composition with slots, then compound components, then hooks or headless primitives. Replace boolean pairs with a variant union.

Your autocomplete shows results for an old query. Why?

Out-of-order responses. I abort the previous request with AbortController, or tag each request with an id and ignore responses that are not the latest. Debouncing reduces the problem but does not fix it.

What belongs in the shared design system?

Generic primitives, tokens and accessible behaviour: buttons, dialogs, comboboxes, tables, an image component, a virtual list. Not domain logic like "CheckoutSummary". Build locally first and extract when the API is proven.

CSR builds the page in the browser (slower first paint, simple hosting); SSR sends ready HTML per request (faster first paint, SEO, needs a server).

Optimistic UI with a temporary client id; replace it with the server's id on ack, or show "failed, retry".

Video is encoded at several qualities in short segments; the player picks the quality for each segment based on current bandwidth (HLS, DASH).

Shareable links, working back button, and pages the server can render and cache.

A words-diagram from the notes (synthesis):

Server/API ⇄ (BFF / GraphQL) ⇄ [Client: Network layer → Data store (normalised cache) → Controllers / hooks → View components]

Side boxes: Service Worker (offline, cache), real-time channel (WebSocket/SSE), telemetry, feature flags.

Analogy. The view is the shop floor. The data store is the stock room. The network layer is the delivery dock. The BFF is a wholesaler who packs exactly the boxes this shop needs.

Requirements checklist (synthesis)
  • Functional: the core 3–4 features only; state what is out of scope.
  • Non-functional: devices and browsers, mobile-first, offline, LCP < 2.5 s and INP < 200 ms, WCAG 2.2 AA, i18n/RTL, SEO, data per page, real-time freshness.
  • Users and traffic shape.

Normalised store (synthesis): entities by id (users, posts) plus ordered id lists per view (feed: [ids]). One update fixes every view. GreatFrontEnd calls normalisation "advanced", used by Facebook (Relay) and Twitter (Redux), but not strictly needed in an interview (GreatFrontEnd, search excerpt).

BFF (Backend for Frontend): one backend per user experience, owned by the UI team, so API and UI change together. Strongly consider it for mobile and third-party consumers; for web it is optional unless you need heavy aggregation or SSR. It should call downstream services in parallel and degrade gracefully (for example drop stock levels if that service fails), so clients must handle partial responses (Sam Newman).

Lessons from real systems
  • facebook.com (2020): code split into three tiers: Tier 1 skeleton and first paint, Tier 2 importForDisplay for above-the-fold, Tier 3 importForAfterDisplay for logging and live subscriptions; importCond for experiment and locale variants; per-product JS budgets with merge-request size checks. Relay @module loads only the renderer a returned type needs, @stream sends feed stories one at a time, @defer delays slow sections, and EntryPoints pair a code split with its query so code and data load in one round trip. The principle: "as little as possible, as early as possible" (Meta Engineering).
  • Slack desktop (2019): React + Redux; one Redux store per workspace holding its data, connection status and WebSocket; a data model assumed partial and lazily loaded; new code reached legacy code only through an adapter; incremental rollout starting with the emoji picker (Slack Engineering).
  • Figma: see Modules 3 and 10 (Figma blog).
  • Video in the browser: the Media Source API feeds SourceBuffers to <video>, giving control over fetch rate and buffer eviction; DASH puts adaptive logic in client JS over plain HTTP/CDN; HLS is another option; ManagedMediaSource lets the browser evict buffers; use WebRTC, not DASH, for real-time (MDN MSE).
Worked HLD approaches (synthesised headline decisions)

News feed (Facebook / Twitter).

  • R: view feed, create post, like and comment, infinite scroll.
  • A: feed list → post component → composer; store; API layer.
  • D: Post, User, Media, Feed {ids, cursor}, normalised.
  • I: GET /feed?cursor&limit → {items, nextCursor}; POST /posts; reactions.
  • O: SSR the first page for LCP; cursor pagination; virtualised list; srcset and lazy images; optimistic likes; a "New posts" banner instead of auto-inserting (no layout shift); tiered code and data-driven component loading (Meta); XSS-safe rendering of user content; aria-live for new posts; <article> landmarks. GreatFrontEnd's newer rubric also expects Core Web Vitals, offline and retries, rendering-time XSS, telemetry, a11y and RTL (GreatFrontEnd, search excerpt).

Chat (WhatsApp / Slack). WebSocket with heartbeat and backoff reconnect; message states sending → sent → delivered → read, with client temp ids reconciled to server ids; backward cursor pagination for history; normalised conversations and messages; IndexedDB cache and outbox; lazy partial data per workspace (Slack); throttled typing and presence; a virtualised reversed list anchored at the bottom; mention end-to-end encryption for WhatsApp.

Video streaming (YouTube / Netflix). HLS/DASH via MSE with adaptive bitrate chosen from bandwidth and buffer level; segments from a CDN; preload only poster and metadata; prefetch the next episode; save resume position periodically; WebVTT captions and keyboard controls; DRM via EME; a browse page of virtualised rows with lazy thumbnails.

E-commerce product page and checkout. SSR/SSG + ISR for SEO and LCP; hero image priority; variant selection in the URL; cart on the server with a local optimistic copy; checkout as a validated step flow with an idempotency key on order submit; never store card data (use the payment provider's hosted fields or iframe to reduce PCI scope); analytics events; A/B flags; Intl for currency and numbers.

Collaborative editor (Google Docs / Figma). WebSocket per document; choose OT (central server, text) vs CRDT (Yjs/Automerge, offline-friendly) vs Figma-style server-authoritative LWW per property for object graphs; local-first apply and reconcile; presence cursors throttled to about 50–100 ms; canvas/WebGL rendering for design tools; per-user undo stack; offline edits replayed on reconnect.

Photo sharing (Instagram). Upload pipeline with client-side resize and compress, preview via object URL, resumable chunked upload, progress and retry; feed as above; AVIF/WebP and responsive images; grid virtualisation; prefetch the next stories.

Others in brief. Maps: vector tiles with WebGL, load visible tiles plus a margin, cache tiles, debounce search on pan, cluster markers. Calendar: store UTC and render in the user's zone, expand RRULE recurrence for the visible range, an overlap layout algorithm, optimistic drag, keyboard grid navigation, fetch by visible range. Dashboard: widget config from the server, each widget fetching independently with its own error boundary, polling or SSE for live data, SWR caching, chart downsampling, filters in the URL.

Architecture at scale

Analogy (from the notes): a monolith is one big house; a monorepo is a housing estate with shared roads and one planning office; micro-frontends are separate houses on separate plots that must still look like one street.

Micro-frontends are "an architectural style where independently deliverable frontend applications are composed into a greater whole". Benefits: smaller codebases, autonomous teams, incremental upgrades, independent deploys. Integration options: build-time packages (discouraged: lockstep releases), server-side composition, iframes, run-time JavaScript entry functions (the author's default), Web Components. Downsides: duplicated dependencies increase payload, dev environments differ from production, and more pipelines need governance (Fowler / Cam Jackson). single-spa distinguishes applications, parcels and utility modules and strongly encourages sharing one instance of big frameworks (single-spa). Module Federation 2.0 adds type hints, a manifest and a runtime plugin system for webpack and Rspack (module-federation.io).

Micro-frontend checklist (synthesis): split by business domain or route, not UI layer; one shell owns routing, auth and layout; share the framework as a singleton; a shared token and design-system package; communicate via URL, custom events or a tiny typed bus, never a shared global store; versioned contracts; an error boundary per MFE; a whole-page performance budget; contract tests in CI.

Build tools. Vite 8 (stable 12 March 2026) replaces esbuild + Rollup with Rolldown (Rust) and Oxc, with builds up to 10–30x faster; Linear's build went from 46 s to 6 s (Vite blog). Turbopack is the default for next dev and next build from Next.js 16, and Rspack 2.0 was reported in April 2026 (secondary source, tech-insider; unverified).

i18n checklist (synthesis): ICU message format for plurals and gender; Intl for dates, numbers, currency and relative time; locale bundles loaded on demand (like Meta's importCond); RTL via CSS logical properties and dir="rtl"; no string concatenation; leave 30–40% room for text expansion; locale in the URL with hreflang.

Release (synthesis): trunk-based development + feature flags; affected-only builds with remote cache; a preview deploy per PR; hashed assets on a CDN; canary (1% → 10% → 100% with automatic rollback on errors or Web Vitals regressions) vs blue-green vs flag-based rollout (cheapest for frontend); keep old asset versions online so open tabs do not 404 on lazy chunks. Treat flags as inventory with expiry dates (Fowler, Feature Toggles). Record big choices as ADRs (Cognitect).

Common mistakes (synthesis)

Jumping into code or a framework before requirements · designing the backend (sharding) in a frontend round · no data model or API shapes · offset pagination for a live feed · ignoring loading, empty and error states · no accessibility · one giant global store for server data · never stating trade-offs · running out of time before optimisations · not checking in with the interviewer.

Final checklist to say aloud

Loading / empty / error states · pagination type · caching and invalidation · optimistic updates and rollback · real-time transport and reconnect · virtualisation · image and code splitting · Web Vitals targets · keyboard and screen reader · i18n and RTL · XSS, CSP and tokens in HttpOnly cookies · telemetry and error logging · feature flags for rollout.

Key takeaways
  • HLD is RADIO across the whole app, with the deep dive carrying the senior signal.
  • Cursor pagination, normalised stores and per-route rendering are default answers for feeds.
  • Real systems (Meta, Slack, Figma) win with tiered loading, lazy partial data, adapters for migration and server-authoritative sync.
  • Default to a modular monolith in a monorepo; adopt micro-frontends only when team independence is worth their payload and operations cost.

Interview questions with model answers

Design a news feed.

Scope: view, post, like, infinite scroll. Architecture: feed list, post, composer, a normalised store and an API layer. API: GET /feed?cursor&limit. Optimisations: SSR the first page, cursor pagination, virtualisation, responsive lazy images, optimistic likes, a "New posts" banner to avoid layout shift, tiered code loading, safe rendering of user content, telemetry and accessible <article> items with polite announcements.

Design a chat app's frontend.

WebSocket with heartbeat and backoff, resync from the last sequence. Messages move from sending to read, with temp ids reconciled to server ids. Backward cursor history, a reversed virtual list anchored at the bottom, IndexedDB cache and outbox for offline, throttled typing, one connection shared across tabs.

Design an e-commerce checkout.

Step flow with validation; cart on the server with an optimistic local copy; idempotency key on order submit so retries do not double-charge; card data only in the payment provider's hosted fields; SSR or CSR, never CDN-cached; analytics and flags; Intl for money.

When would you choose micro-frontends?

When many teams need independent release cycles, or during a strangler migration from legacy. I start with a route-level split behind a proxy because it is cheapest. I share the framework as a singleton, keep communication through the URL and events, and accept the cost in duplicated dependencies and extra pipelines. For 1–3 teams, a modular monolith in a monorepo is better. Full visual notes: Micro frontend architecture.

Do we need a BFF?

Yes for mobile or third-party clients, or if the web needs heavy aggregation, SSR or token handling (RFC 10017's BFF pattern). It should be owned by the UI team, call services in parallel and degrade gracefully. Otherwise it is optional for web.

How would you migrate a large legacy frontend?

Incrementally, like Slack: new code in a separate area, reaching legacy only through an adapter; move one feature at a time behind flags; keep old asset versions online during rollout; record the decision in an ADR.

E Real examples and use cases

Zalando 2016–2021

from page fragments to one composition framework

Illustrates: Architecture at scale (micro-frontends)

What Project Mosaic built pages from fragments with Tailor, a Node.js streaming layout service (2016). From 2018 they replaced it with the Interface Framework, which composes views from "entities" and "renderers" and lets teams migrate page by page.

Why Many teams had to ship one website. Fragments were web-only and hard to keep consistent.

Result About 90% of traffic went through the Interface Framework by March 2021.

Lesson Micro-frontends have a lifecycle: split first, then consolidate on a shared framework.

Source: Zalando 2016; Zalando 2018; Zalando 2021, Part 1 See it: Part 1 and Part 2: diagrams of fragments vs renderers (not verified).

Shopify 2021–2026

third-party checkout UI runs in a worker sandbox

Illustrates: Lessons from real systems; Architecture at scale

What Third-party checkout extensions run in a web worker. Their code describes the UI and sends it by message passing, and the host draws it with trusted components ("remote rendering", open-sourced as remote-ui). Shopify is moving to remote-dom and Polaris web components.

Why Apps must never touch payment data or the checkout DOM, and checkout must stay fast.

Result Extensions always run in a worker. A 64 KB gzip limit per extension bundle is reported (unverified: secondary sources).

Lesson A real answer to "how do you sandbox third-party UI and cut payment risk".

Source: Shopify Engineering: Remote Rendering; shopify.dev; InfoQ, Oct 2026 See it: Remote Rendering post: host and worker diagrams (not verified).

Netflix 2017–2018

server-rendered landing page, client React deferred

Illustrates: Worked HLD approaches (video streaming); Module 6 Rendering architectures

What Kept React on the server but removed client React and several libraries from the logged-out home page. Then prefetched React, HTML and CSS for the sign-up flow.

Why The first interaction did not need a client-side app.

Result Time to Interactive fell by more than 50%, and over 200 KB of JavaScript was removed. Prefetching made later steps about 30% faster. (TTI is now a retired metric.)

Lesson Server-render first, then defer and prefetch client JS. React was deferred, not removed from the codebase.

Source: Addy Osmani, "A Netflix Web Performance Case Study"; Jake Archibald, 2017 See it: Osmani's post: waterfall and bundle charts (not verified).

Google Docs 2021

moved rendering from DOM to canvas

Illustrates: Worked HLD approaches (collaborative editor)

What Moved document rendering from HTML/DOM to canvas, rolled out over months.

Why Better performance and the same display on every platform.

Result Some Chrome extensions broke, so admins got a test document. Google said screen readers would not be affected; a separate accessibility layer is still needed.

Lesson Canvas needs a parallel accessible DOM. Plan both.

Source: Workspace Updates, May 2021; The New Stack See it: Workspace Updates post (not verified).

Facebook 2015–2017

feature flags at billions of checks a second

Illustrates: Architecture at scale (feature flags)

What Code ships to production turned off. Gatekeeper then turns it on step by step for chosen users, such as employees or 1% of users of one phone model. Configerator manages the configs with code review and canary tests. facebook.com moved to near-continuous "push from master" in April 2016.

Why Ship often without risking everyone at once.

Result Gatekeeper runs billions of checks a second and uses a significant share of frontend cluster CPU. Mobile teams grew 15x while critical release issues stayed almost flat.

Lesson Evaluate flags once per request or session and cache the result (an inference).

Source: SOSP 2015 paper; Adrian Colyer summary; Meta Engineering, Aug 2017 See it: Meta 2017 post: a release pipeline diagram (not verified).

SoundCloud 2013–2021

started the BFF pattern, then found its limits

Illustrates: Architecture at scale (BFF)

What Built one backend per user experience (Backend for Frontend). SoundCloud says it started this in 2013. Phil Calçado wrote it up in 2015.

Why Different clients needed different data shapes.

Result In 2021, SoundCloud engineers said that treating the BFF "as an extension of the client" caused duplicated logic and bloat in some cases.

Lesson A BFF should combine and shape data, not hold business logic.

Source: SoundCloud developers blog; philcalcado.com, 2015; InfoQ, 2021 See it: SoundCloud architecture post: service diagrams (not verified).

Spotify 2021

merged desktop and web into one shared UI

Illustrates: Architecture at scale (micro-frontends, moving away)

What Unified the desktop client and the Web Player into one web UI. The desktop app is a native shell around Chromium Embedded Framework.

Why The two clients had drifted apart. Secondary sources say the old desktop client used iframe micro-frontends unverified.

Result One codebase for desktop and web. A small team proved the idea in about 3 months.

Lesson Sometimes the right move is to un-split.

Source: Spotify Engineering, Apr 2021; InfoQ, 2021 See it: Spotify 2021 post (not verified).

Disney+ Hotstar 2019

25.3M concurrent viewers

Illustrates: Worked HLD approaches (live video)

What Served 25.3M concurrent viewers in the 2019 Cricket World Cup semi-final. The team pre-scaled in "ladders" per million users, ran "Game Day" load tests, and built clients to degrade gracefully.

Why Traffic jumps with match moments, such as when a star batsman gets out.

Result Peak handled (secondary sources only; they disagree on growth per minute).

Lesson For a frontend round, the lesson is graceful client degradation under load, not CDN details.

Source: Rootconf 2019 talk; System Design newsletter See it: AWS user group slides: architecture slides (not verified).

Google 2016

one monorepo for the whole company

Illustrates: Architecture at scale (monorepos)

What Keeps one repository with trunk-based development, plus tools for static analysis, code cleanup and code review.

Why One source of truth for tens of thousands of developers.

Result 86 TB, about 2 billion lines of code, 9 million source files.

Lesson A monorepo needs strong tooling to work at scale.

Source: Potvin & Levenberg, CACM 2016 See it: CACM article: figures of commit growth and workflow (not verified).
