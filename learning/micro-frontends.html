In plain words

🌱 In plain words

Think of a shopping mall. Each shop has its own owner, staff and opening plan. The mall owns the corridors, signs and security desk. A shop can refit while the others stay open. Micro frontends build a website the same way.

Words to know

Micro frontend (MFE)
One piece of the UI, built and deployed by one team.
Shell (host, container)
The thin outer app: header, login, routing. It loads the pieces.
Remote
A micro frontend that the shell loads at run time.
Composition
How the pieces are put together into one page: at build time, on the server, at the edge or in the browser.
Vertical split
One team per page or route (/search, /checkout).
Horizontal split
Several teams' widgets on the same page.
Modular monolith
One app with strict module boundaries, deployed together.
BFF
Backend for frontend: a small server that holds tokens and shapes data for the UI.

1.1 The mall

🏬The mall building= the shell
🏪One shop= one micro frontend
🧑‍🤝‍🧑The shop's own staff= one team, end to end
🔧Refitting one shop= an independent deploy
🪧The mall's sign rules= the shared design system
🚶Walking between shops= navigating by URL

1.2 The definition

"independently deliverable frontend applications are composed into a greater whole"Cam Jackson, martinfowler.com (2019), still the reference
1 teamowns one business slice, from database to UI
Ship aloneeach part deploys on its own: the hard requirement
Share littleone framework baseline, a design system, singletons
The one ideaMicro frontends solve an organisational scaling problem, not a technical one.

  • One team owns one slice, end to end
  • Each slice ships on its own

  • It is an org-chart decision, not a code-size fix

Why it exists: teams and Conway's Law

🌱 In plain words

Teams split the backend into services, but left one shared UI on top. Every release still waited for everyone. Micro frontends carry the split all the way up to the screen.

Words to know

Front-end monolith
One shared UI on top of many backend services.
Conway's Law
Systems end up shaped like the teams that build them.
Inverse Conway manoeuvre
Draw the boundaries where you want the team boundaries.
Bounded context
One business area with its own words and rules (search, checkout).

2.1 From one UI to one slice per team

  1. 1Three teams, one frontend. Everyone edits one codebase.
  2. 2One release train. A change from one team waits for all the others.
  3. 3The "front-end monolith". The backend is already split into services, but one UI sits on top. That cancels most of the benefit.
  4. 4Inverse Conway. Draw UI boundaries where you want team boundaries. Each team owns a vertical slice, database to UI.
  5. 5Each slice ships alone. Independent deployment is the hard requirement.
  6. 6Many teams? AWS adds an enablement team (UI library, standards, performance budgets) and a platform team (CI/CD, runtime, monitoring).
"Architecture can significantly shape organizational structure"Luca Mezzalira, QCon SF, November 2025 (InfoQ)
Honest noteNone of the sources names Conway's Law. Linking it here is an interpretation, but a standard one.

3

When to use it, and when to avoid it

🌱 In plain words

Micro frontends cost money every day. Pay that cost only when teams are really blocked on each other's releases, or when you must move a legacy app across piece by piece.

Words to know

Version skew
Different parts run different versions at the same moment.
Strangler fig
Replace an old app one route at a time, until nothing old is left.
Distributed monolith
Split into parts that still must deploy together. The worst of both.

3.1 What you gain, what you pay

You gain

  • Independent releases per team
  • Smaller codebases, lower cognitive load
  • Step-by-step (strangler-fig) migration with rollback
  • Vercel: >40% faster preview builds and local compilation
  • DAZN: new teams contributed in week one

You pay

  • Non-atomic releases: versions skew
  • Duplicate deps: React + react-dom were ~50% of the bundle in Jackson's example
  • More repos, pipelines, servers, governance
  • Harder end-to-end tests and debugging
  • Runtime failures one app never has
Evidence checkNo controlled study measures productivity or performance before and after. The evidence is vendor reports and practitioner stories.

3.2 The decision ladder

Nx, in one lineFederation "adds runtime failure modes without removing any release bottleneck" when teams already deploy together. Use micro frontends when independent deployment is a hard requirement.

3.3 Vercel's thresholds

< 5developers: do NOT use micro frontends
< 3 minbuild time: do NOT use them
> 5 minbuild time: one signal to consider them
3 or moresignals true: consider micro frontends

🚫 Red flags (any one = no)

✅ Signals (need 3 or more)

Tick what is true for your team.

AWS addsMicro frontends are not recommended for a centralised organisation using waterfall.

S The failure to recognise: the distributed monolith

Parts that are split but share state or must deploy together. They "can only live together" and combine the drawbacks of both designs (heise).

Coordinated deploysShared global storeSeveral frameworks, no migration planEvery team ships its own ReactBusiness logic in the shell

Why the modular monolith is the default: clear module boundaries, tested separately, deployed together. No gateways, discovery or distributed logging, and modules can still be pulled out later.

Key takeaways

  • Default: modular monolith in a monorepo
  • Split only for a measured release bottleneck
  • Vertical first, horizontal later
  • Build-time pain alone? Use caching, not MFEs

How to split: vertical vs horizontal

🌱 In plain words

Vertical: each team owns whole pages. Horizontal: several teams share one page, like stalls at a market table. Start vertical. It is much simpler.

4.1 One page of fragments vs one team per route

  1. 1Horizontal: the shell draws the frame (header) of one page.
  2. 2Team Product's fragment fills the main area.
  3. 3Other teams add a recommendations widget and a mini-cart. Three teams, one screen: they must coordinate at run time.
  4. 4Vertical: /search is a whole page from Team Search.
  5. 5Open a product: /product/42 is a whole page from Team Product.
  6. 6Go to /checkout: Team Checkout. Each team ships its pages without touching the others.

↕️ Vertical (by route)

One team per page. Plain links can route. Start here.

simpleSEO friendly

↔️ Horizontal (by fragment)

Several teams on one page. Adds "immediate complexity and should be deferred" (InfoQ).

deferharder testing

4.2 Mezzalira's decision order

DefineVertical or horizontal
ComposeClient, server or edge
RouteWho owns which URL
CommunicateURL, props, events
"Micro frontends are the technical representation of a business subdomain"InfoQ, 2025

Split by

  • Business subdomain (search, product, cart/checkout, account, content)
  • First-level URL for a migration
  • Boundaries found with domain storytelling

Don't split by

  • Widgets: a button or header is not an MFE ("nano frontends")
  • Code size alone
  • Pages users jump between all the time

Key takeaways

  • Vertical by route first
  • Horizontal only where widgets must share a page
  • One MFE = one business subdomain
  • Order: define → compose → route → communicate

Composition techniques

🌱 In plain words

Composition is where the pieces get glued together: when you build, on the server, at the CDN edge, or in the browser. Each place trades isolation, speed and SEO differently.

Words to know

SSI / ESI
Server Side Includes / Edge Side Includes: the server or CDN pastes HTML fragments into a page.
Fragment
A piece of HTML owned by one team (Podium calls it a "podlet").
Edge
CDN servers close to the user.
Import map
A browser list that maps module names to URLs.

Jackson's original list: server-side templatesbuild-time packagesiframesrun-time JavaScriptWeb Components

5.1 Seven techniques, one card each

5.2 Server composition, step by step (Podium / ESI)

  1. 1The browser asks for a page. The layout server (or a CDN running ESI) gets the request.
  2. 2It has registered every fragment (Podium "podlets") by manifest URL.
  3. 3It fetches every fragment in parallel, with context headers.
  4. 4On an error or timeout, it uses a cached fallback.
  5. 5Podium sends the asset list early as an HTTP 103 Early Hint.
  6. 6It injects the fragment HTML plus the collected CSS and JS, and returns one document.

5.3 Edge fragment piercing (Cloudflare)

  1. 1A gateway Worker at the edge receives /login.
  2. 2It makes parallel sub-requests: one to the legacy app, one to an SSR fragment.
  3. 3It streams the fragment first. The fragment is interactive immediately.
  4. 4When the legacy app renders, the fragment's DOM is "pierced" into its outlet without losing state.
  5. 5The successor, Web Fragments, runs each fragment's JS in its own context but shares the DOM, navigation and history. Pre-1.0: treat as experimental.

Module Federation deep dive

🌱 In plain words

The host page asks: "Give me the Button from app1". The browser fetches app1's file list, agrees on one shared copy of React, downloads the Button and shows it. No rebuild of the host.

Words to know

Share scope
The runtime's list of shared packages and their versions.
Singleton
Only one copy may load (React must be one).
mf-manifest.json
A remote's description file (classic: remoteEntry.js).
Exposed module
What a remote offers to others, e.g. app1/Button.

6.1 The runtime load, step by step

  1. 1The host boots and initialises the share scope with its shared deps.
  2. 2Code hits loadRemote('app1/Button').
  3. 3The runtime fetches the remote's mf-manifest.json (or classic remoteEntry.js).
  4. 4The remote registers its shared deps into the share scope.
  5. 5Negotiation picks one version per shared package (singleton, requiredVersion).
  6. 6The runtime downloads the exposed module's chunks and CSS.
  7. 7The host renders (mounts) the Button, using the one shared React.

6.2 The shared switches

OptionEffect
singleton: trueOnly one version loads. The higher wins; the lower side gets a warning
requiredVersionRange check. Too low = console warning
eager: trueBundles the dep into the entry, which "can greatly increase" its size
shareStrategy: 'version-first' (default)Loads all remote entries at startup. An offline remote can break startup
shareStrategy: 'loaded-first'Reuses loaded deps, loads remotes on demand. Suggested for production with network risk
Why React must be a singletonHooks and context break with two copies. Treat a framework major upgrade as a coordinated platform event; leave everything else to teams.
For developers
// a typical shared config
shared: {
  react:       { singleton: true, requiredVersion: '^19.0.0' },
  'react-dom': { singleton: true, requiredVersion: '^19.0.0' }
}

// in the host
loadRemote('app1/Button')

6.3 What MF 2.0 added on top of webpack 5's idea

⚙️ Standalone runtime

Not tied to one bundler.

📄 Manifest

mf-manifest.json describes each remote.

🔤 Dynamic type hints

Generated @mf-types for TypeScript.

🔌 Runtime plugins

Hook into loading.

🛠️ Chrome DevTools

Inspect remotes and shares.

🅰️ Native Federation

Angular's esbuild world: remote metadata becomes a native import map.

S Senior points

  • Module Federation does not by itself guarantee independent deploys (GreatFrontEnd). You still need per-MFE pipelines and a manifest pointer.
  • Pick import maps or Module Federation, not both (single-spa).
  • For Vite, use @module-federation/vite; the old @originjs plugin is inactive since 2025.
  • Types via @mf-types are always current but need a fetch at build time (default timeout 2000 ms).

Key takeaways

  • Host → manifest → share scope → one version → chunks → mount
  • React and react-dom: singletons
  • Prefer loaded-first when remotes can be offline
  • MF alone ≠ independent deploys

Routing and communication

🌱 In plain words

The shell owns the main roads (top-level URLs). Each team owns the streets inside its area. Teams talk through the URL and short event messages, never by reaching into each other's memory.

Words to know

activeWhen
single-spa's rule for which URL turns an app on.
CustomEvent
A browser event with your own name and data.
Global store
One shared state object (like shared Redux). Rejected here.

7.1 single-spa lifecycle

  1. 1The URL changes. single-spa checks every app's activeWhen.
  2. 2Apps going inactive get unmount: clean DOM and listeners.
  3. 3Newly active apps load, via an import map or import().
  4. 4bootstrap runs once, the first time only.
  5. 5mount renders into the app's DOM container.

🛣️ Hierarchical routing

Shell owns top-level paths. Each MFE owns sub-routes under its prefix.

🔗 URL = the contract

Fowler uses /restaurant/:id as the interface between MFEs. Test such routes automatically.

⚡ Hide hard navigations

Vercel prefetches assets when a link becomes visible and prerenders on interaction with Speculation Rules.

Classic failure: a router per MFEEvery router calls the History API, but routers only hear popstate, not pushState. The back button becomes unpredictable unless shell and children sync explicitly.

7.2 How MFEs talk

  1. 1URL: navigable state (selected item, filters) lives in the URL. Both MFEs can read it, and deep links work for free.
  2. 2Props: the shell passes data down to an MFE as props or attributes.
  3. 3Events: Product dispatches CustomEvent('cart:item-added@v1') on window.
  4. 4Cart listens and updates its badge. Neither knows the other's code.
  5. 5Shared server data comes from the backend, a BFF or a cache module, not a store.
  6. 6No global store. AWS: shared Redux "creates significant coupling". If two MFEs chat constantly, merge them.
NeedUse
🔗 Navigable stateURL path and query
⬇️ Shell → MFE dataProps or attributes
📣 Sibling noticewindow.dispatchEvent(new CustomEvent('cart:item-added@v1', { detail }))
🗄️ Shared server dataBackend, BFF or a cache module
🗂️ Cross-tab sync (logout everywhere)BroadcastChannel (same origin only)

S Senior points

  • AWS: an event bus distributed as a library, standard DOM events, and a shared wiki page listing every event (an event catalogue).
  • single-spa: "if two frequently exchange state, consider merging them".
  • Where sharing is unavoidable, opt in to read-only sharing through defined interfaces.
  • Event naming (domain prefix, @v1 suffix, additive-only changes) is inferred from microservice practice; no source states it as a rule.
  • OWASP: an in-page bus has no browser-enforced identity, so don't treat event names as proof of authority.

Key takeaways

  • Shell owns history and top-level paths
  • URL > props > events
  • No global store
  • Chatty MFEs = wrong boundary

Shared dependencies, styling and the design system

🌱 In plain words

Share the big, heavy things (React) as one copy. Let small libraries be copied. Share the look through design tokens (colour, spacing variables) so every team's pages feel like one site.

Words to know

Design token
A named design value, like --brand, usually a CSS custom property.
Shadow DOM
A browser wall that keeps outside CSS out of a component.
Cascade layers
CSS @layer: decides which styles win in a fixed order.

8.1 Three viable strategies (AWS)

🚫 Share nothing

Each MFE bundles its own deps.

🗺️ Web standards

Import maps.

🧩 Module Federation

Runtime share scope.

Everything elseAWS calls other approaches "generally anti-patterns".

Share

  • Big libraries (React, rxjs) as in-browser modules
  • Framework singletons
  • A versioned design system
  • UI logic only

Don't share

  • Small libs like react-router: let them duplicate
  • Domain logic: no shared ProductTable (Fowler)
  • A component library built too early

Shared deps must be upgraded together (single-spa).

8.2 The design system: package or federated?

📦 Versioned npm package

Most common. Tokens are the shared contract.

deterministicreviewablefixes roll out slowly

📡 Federated at run time

One update reaches every MFE at once.

instant rollouta bug ships everywhere

8.3 Styling layers

Tokens CSS custom properties, shared
Design-system components versioned package
MFE-scoped styles CSS Modules or a prefix
Optional Shadow DOM boundary per widget

S Senior points

  • Fowler: "the approach that you pick does not matter all that much" if styles compose predictably (BEM, Sass nesting, CSS Modules, CSS-in-JS, Shadow DOM).
  • Prefixing: postcss-prefix-selector (single-spa ecosystem).
  • Cascade layers make overrides deterministic, but if two versions of one library emit into the same layer, load order still decides.
  • Global resets and fonts belong to the shell only.

Key takeaways

  • Big libs shared, small libs duplicated
  • Import maps or MF, not both
  • Tokens are the contract; they cross Shadow DOM
  • Share UI logic, never domain logic

Security and performance

🌱 In plain words

Separate repos are not separate rooms in the browser. Every piece on a page can touch everything else. And many small pieces can mean many slow round trips, unless you plan for them.

9.1 One page = one trust zone

OWASP, the anchorRemote JavaScript, Module Federation included, runs with the host page's full privileges. Another origin does not sandbox it. Shadow DOM does not isolate scripts.

🔑 Login

Shell owns authentication.

🍪 Tokens

Server-side behind a BFF; HttpOnly Secure cookie + CSRF protection. Never in localStorage.

🛂 Authorisation

On the server, every request.

📥 Loading remotes

Only approved HTTPS URLs from host config. Never from query parameters.

🧾 Integrity

SRI on entries and dynamic chunks; immutable, reviewed releases.

🧱 CSP

Host's CSP applies. An allowed source is still trusted code.

📦 Less-trusted features

Sandboxed iframe on its own origin. Never allow-scripts + allow-same-origin on the host origin.

✉️ postMessage

Exact targetOrigin; check event.origin and event.source; validate data.

🗝️ Deploy credentials

Separate per shell and per remote. Keep a known-good release for rollback.

2019 (Fowler's example)

  • Container injects the token into each MFE

Now (OWASP)

  • Tokens stay out of the browser: BFF + HttpOnly cookie

9.2 Performance: help or hurt

6 MB → 3 × 2 MBAWS's illustrative per-route split; "might improve first-load performance by up to 300 percent" (not measured)
~50%React + react-dom share of the bundle in Jackson's example app
7 tripsin the loading waterfall below
preloadRemote / manifest prefetchsingleton framework depsloaded-first sharinglazy per-route loadingSSR or server composition for the critical path
Budgets nobody ownsNo single team owns total page weight, so enforce a per-MFE bundle budget in every pipeline. Mezzalira calls these fitness functions.

Key takeaways

  • Same page = one trust zone
  • Tokens behind a BFF, HttpOnly cookie
  • Remote URLs only from host config, with SRI
  • Kill the waterfall; budget each MFE

Testing, deployment and observability

🌱 In plain words

Every release is a new file that is never overwritten. One small list (the manifest) says which file is live. To undo a bad release, you just point the list back.

Words to know

Immutable asset
A file that never changes once uploaded (new version = new name).
Canary
Send a small share of users to the new version first.
Contract test
Checks the agreement at a seam (event shape, props, route) without the other team's app.

10.1 Testing: a pyramid per MFE plus contracts

Thin end-to-end "is the page assembled correctly"
Contract tests at the seams events, typed props, routes
Comprehensive unit tests inside each MFE

📚 Storybook Composition

One Storybook browses others by URL: each MFE's, or the design system's.

🏗️ Integrate early

Standalone dev differs from the container, so test in production-like environments (Fowler).

⚠️ Vercel found

Cross-MFE local and preview testing hard; horizontal splits made testing, releasing and debugging harder.

10.2 Deploy: immutable files, one pointer, canary, rollback

  1. 1The pipeline uploads catalog-1.3.5.js to the CDN as a new file, never overwriting.
  2. 2It updates the one mutable pointer (import map or discovery manifest) through an API. Canary: weighted entries, starting at 10% of users.
  3. 3The shell fetches the manifest at boot and loads the chosen remote. The ramp adds 10% a minute.
  4. 4A monitoring alarm fires and stops the ramp.
  5. 5Rollback = repoint the manifest. No rebuild. The issue hit about 20% of users instead of 100%.
For developers
// AWS frontend discovery schema: one array per MFE
{ url, fallbackUrl,
  metadata:   { integrity, version },
  deployment: { traffic, default } }
// e.g. v1.2.2 at traffic: 30 and v2.0.0 at traffic: 70

🔒 Concurrent deploys

single-spa's import-map-deployer is safe for them.

🚦 Vercel's migration

Feature flags moved traffic; old code deleted only after a page served traffic a week without errors.

⚙️ Environment config

In the manifest per environment, not baked into bundles.

10.3 Observability: one crash must not blank the page

ErrorBoundaryfallback: "MFE unavailable"
Suspensefallback: skeleton
Remotecatch load failures around import()
mfemfe_versionteamtag every error, web-vitals beacon and log

🛟 CDN failover

The manifest's fallbackUrl.

📮 Sentry

Bundler plugins add module metadata; makeMultiplexedTransport routes errors to a project per MFE. Sentry.init() once; same SDK version everywhere.

  <Suspense fallback={<Skeleton/>}>

  </Suspense>

S Developer experience: run one, borrow the rest

  • Run only your MFE locally; point the others at deployed versions. single-spa's import-map-overrides toggles each one in an in-browser UI.
  • Repo strategy is contested: single-spa discourages monorepos; Vercel used Turborepo + Dependency Cruiser and kept independent deploys.
  • A monorepo does not mean coupled deploys. What matters: independent pipelines and enforced import boundaries.

Key takeaways

  • Unit tests inside, contracts at seams, thin E2E
  • Immutable files + one mutable pointer
  • Canary by weights; rollback by repointing
  • Error boundary + owner tags per MFE

🌱 In plain words

Companies that gave each team clear pages to own did well. Companies that let every team pick its own tools later pulled back, because the site felt inconsistent and was hard to learn.

Source caveatsDAZN's write-ups conflict slightly (separate frontend and backend teams, Tailor.js); the likely reading is a vertical split by view on the frontend only. DAZN chose copy-paste over shared components. PayPal and American Express are often cited for server-side composition, but no primary write-up with numbers was found.

11.3 Why they pulled back

Spotify left iframes because

  • Too many web technologies hurt onboarding
  • Features built twice (desktop and web)
  • The desktop app was very hard to make accessible

Zalando left free-form fragments because

  • Different stacks and deploy practices gave an inconsistent UX
  • Contributing meant running your own fragment, data sources, tracking and A/B setup
  • The new model blurred ownership
The shared lessonKeep team ownership, but standardise the stack and the design system. Most regrets come from using micro frontends to fix a code-size problem when the real need was module boundaries.

One team that dropped micro frontends (dev.to, anecdotal) said autonomy did not replace alignment, and the shell plus several MFEs "crushed laptops" in local dev. It moved to a modular monolith with lint-enforced boundaries.

Key takeaways

  • IKEA, DAZN, Vercel: clear vertical ownership
  • Spotify, Zalando: consolidated the stack
  • Keep ownership, standardise the stack
  • Migrate route by route behind a thin shell
12

Anti-patterns and their fixes

🌱 In plain words

Ten ways teams get micro frontends wrong. Each one has a short symptom you can spot and a fix.

🔬 Nano frontends

A button or header becomes an MFE.
Fix: one MFE per subdomain; components for shared UI.

🐉 Multi-framework page

Several frameworks load on one page.
Fix: only during migration or acquisition.

🔪 Swiss Army Knife comms

Events + web storage + SystemJS, all mixed.
Fix: one convention; anti-corruption layer for legacy.

🔗 Dependencies hell

Shared core libs force lock-step upgrades.
Fix: few shared libs; tolerate minor drift.

🔁 Bidirectional data flow

Host and remote mutate each other's state.
Fix: unidirectional flow.

🌍 Global shared state

Changing state shape needs every team.
Fix: pub/sub events with documented inputs and outputs.

🔨 Hammer the APIs

Several MFEs call the same endpoint.
Fix: rethink the split, or fetch once in a container.

🧠 Logic in the shell

The shell team becomes a bottleneck.
Fix: shell = routing, config, orchestration only.

🧭 Router per MFE

Broken back button.
Fix: shell owns history; children sync.

⛓️ Distributed monolith

A cannot ship without B.
Fix: fix the boundary or merge them.

Sources: the first seven from Mezzalira's 2023 catalogue; shell logic from his 2025 talk; router problem from practitioner write-ups; distributed monolith from heise.

Do

  • Split by business subdomain, vertical first
  • One framework baseline, one design system
  • URL and events for talking
  • Thin shell

Don't

  • Make widgets into MFEs
  • Share a global store
  • Let every team run its own router
  • Ship coordinated deploys and call it independent

Key takeaways

  • Too small: nano frontends
  • Too coupled: global state, bidirectional flow
  • Too clever: logic in the shell, router per MFE
  • A cannot ship without B = distributed monolith
13

The interview answer

🌱 In plain words

Interviewers test judgement. Name the cheaper option first. Then justify the split with a measured team or deploy bottleneck, and say the costs out loud.

13.1 "When would you choose micro frontends?"

Say yes when

  • Several (roughly 5+) autonomous teams own distinct domains
  • Independent release cadence is a measured bottleneck
  • A legacy app must move route by route
  • An acquired app must be integrated

Say no when

  • One or two teams
  • Tight UX coupling across the page
  • The pain is only build time (monorepo caching, "affected" builds)
  • "We might scale someday"
"Micro frontends solve an organisational problem. I'd start with a modular monolith in a monorepo, with enforced boundaries. I'd move to vertical micro frontends only when several teams are measurably blocked on shared releases, and I'd accept the costs: duplicate bundles, version skew and harder end-to-end testing."Model answer from the report

13.2 "Design an e-commerce frontend for 20 teams"

SplitDomains → stream-aligned teams, vertical by route
ComposeServer or edge for SEO and LCP; thin shell
ContractsURL, versioned events, BFF; no global store
ShareOne framework, versioned design system, singletons
PlatformCI templates, budgets, observability, manifest, canaries
RisksEach with a fix; "when would we consolidate back?"

🛒 Domains to name

search, product, cart/checkout, account, content

🏢 Proof for "compose on the server"

IKEA and Zalando composed on the server.

⚠️ Risks to list

Duplicate bundles, inconsistent UX, chatty APIs, version drift, local dev pain.

📊 Variant: internal dashboard

Swap step 2 for a client-side shell (Module Federation or single-spa): SEO matters less. Cite Capital One and SAP Luigi.

13.3 Proof points to memorise

Week oneDAZN: 100+ developers, new teams productive in week one
~90%Zalando: traffic on its unified framework
>40%Vercel: faster preview builds and local compilation

The closing lineA micro frontend system succeeds or fails on its platform team. Calendly: "Microfrontends need a platform, not just a boundary".

Q Flashcards

What problem do micro frontends solve?

An organisational scaling problem: many teams blocked on one release. Not a code-size problem.

The one hard requirement?

Independent deployment. Without it, use a modular monolith.

Vertical or horizontal first?

Vertical by route. Add horizontal splits later, only where widgets must share a page.

Why must React be a singleton?

Hooks and context break with two copies.

How do MFEs talk?

URL > props > events > read-only interfaces. Never a global store.

How do you roll back an MFE?

Repoint the manifest or import map to the previous immutable file. No rebuild.

Where do auth tokens live?

Server-side behind a BFF, with an HttpOnly Secure cookie. Never in localStorage.

What did Spotify and Zalando teach?

Keep team ownership, but standardise the stack and the design system.

Key takeaways

  • Cheaper option first: modular monolith
  • Justify with a measured bottleneck
  • Six steps: split, compose, contracts, share, platform, risks
  • End with "when would we consolidate back?"

Quick quiz

Which is the one requirement that justifies micro frontends?
  1. A large codebase
  2. Using several frameworks
  3. Teams that must deploy independently
  4. Slow builds
C. Independent deployment. Large code or slow builds alone call for a modular monolith and build caching.
Four developers, a 2-minute build. What do you choose?
  1. Module Federation
  2. A single app or modular monolith
  3. single-spa
  4. Edge fragments
B. Vercel's thresholds: under 5 developers or a build under 3 minutes means don't use micro frontends.
Your first split should usually be…
  1. Vertical, by route
  2. Horizontal, by widget
  3. By framework
  4. By file size
A. Horizontal splits add immediate complexity and should be deferred.
An SEO-heavy shop with separate domains. Which composition fits best?
  1. iframes
  2. Module Federation in the browser
  3. Build-time npm packages
  4. Route split or server/edge composition
D. Route split and server composition give full SEO. Build-time packages re-couple releases.
In Module Federation, what does singleton: true do?
  1. Loads the remote only once a day
  2. Only one version of the package loads; the higher wins
  3. Bundles the dep into the entry
  4. Turns off sharing
B. One version loads; the lower side gets a warning. eager is the one that bundles into the entry.
Product wants to tell Cart "item added". What do you use?
  1. A shared Redux store
  2. Import Cart's code into Product
  3. A versioned CustomEvent on window
  4. localStorage polling
C. Events for sibling notices. AWS, Fowler and single-spa all reject a shared global store.
A release is bad. What is the fastest safe rollback?
  1. Repoint the manifest to the previous immutable file
  2. Rebuild the shell
  3. Overwrite the file on the CDN
  4. Ask every team to redeploy
A. Immutable assets + one mutable pointer: rollback is a pointer change, no rebuild.
Remote JS is loaded from another origin with Module Federation. Is it sandboxed?
  1. Yes, by the origin
  2. No: it runs with the host page's full privileges
  3. Yes, if it uses Shadow DOM
  4. Only in production
B. OWASP: another origin does not sandbox it, and Shadow DOM does not isolate scripts. Use a sandboxed iframe for less-trusted code.
